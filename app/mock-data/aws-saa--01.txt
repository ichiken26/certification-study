# 01 セキュアなアーキテクチャ / 認可境界
@multi|あるSaaSの顧客は、それぞれ異なるAWSアカウントを所有する。SaaS運営者のバッチが顧客のS3からファイルを読み込む。長期キーを配布せず、別顧客が他社のロールを指定しても引き受けられないようにしたい。適切な対策を2つ選べ。|クロスアカウントロールの信頼と、顧客ごとに異なるExternalIdを組み合わせる。|1,3|各顧客のアカウントで必要なS3権限だけを持つロールを作成しSaaS主体を信頼する|STSによる一時認証と最小権限を実現する。|全顧客に同じアクセスキーを発行する|長期キーとテナント間権限分離の要件に反する。|ロール信頼ポリシーで顧客固有のExternalIdを要求する|第三者に対する混乱した代理問題への対策となる。|S3バケットを公開する|非公開データの認可を壊す。|S3のオブジェクト名に顧客名を含めるだけ|名前はアクセス制御ではない。
@multi|オンプレミスのバッチがEC2を作成する必要がある。既存企業のX.509認証局を利用でき、AWSアクセスキーをファイルに保存したくない。適切な対策を2つ選べ。|IAM Roles Anywhereで企業証明書を信頼し、必要なAWSロールへの一時認証を行う。|1,4|対応するIAM Roles Anywhereの信頼アンカーを設定する|企業CAを信頼する基盤となる。|EC2インスタンスプロファイルをオンプレミスOSに直接関連付ける|EC2インスタンスプロファイルはEC2の機能である。|S3の署名付きURLをEC2 APIの認証に使う|署名付きS3 URLは任意のEC2 API用資格情報ではない。|必要権限のIAMロールとRoles Anywhereのプロファイルを設定する|短期認証情報の権限を必要範囲に限定する。|rootユーザーのキーを環境変数に置く|長期の強権限資格情報を回避する要件に反する。
S3のゲートウェイエンドポイントと限定したバケットポリシー|開発者はプライベートVPCから機密データのS3バケットを参照する。既存のIAM権限は適切で、ネットワーク経路以外から同バケットにアクセスすることを禁止したい。最も適切な設計は？|S3ゲートウェイエンドポイントで経路を確立し、対応するaws:SourceVpce条件等でバケットアクセスを制約する。|S3のBlock Public Accessだけを有効にする|公開アクセスの抑止には有効だが認証済み主体の経路制約を実現しない。|NAT Gatewayとインターネットゲートウェイを配置する|外部経由のアクセスを制限できない。|バケットをS3 Standard-IAへ移行する|保管クラスの変更はアクセス経路の制御ではない。
CloudFront OACとS3バケットポリシー|ゲームのアップデートファイルを世界各地に配信する。S3のURLへの直接アクセスは禁止するがCloudFrontからは取得できるようにしたい。最小の運用負荷で実現する設計は？|非公開S3オリジンにOACを設定し、対象配信からの読取をバケットポリシーで認可する。|S3静的ウェブサイトエンドポイントを公開する|直接公開アクセスの禁止と相反する。|全利用者にS3読取IAMユーザーを発行する|運用負荷が高くCloudFront経由限定にならない。|S3のCORS設定だけでCloudFrontのドメインを許可する|CORSはブラウザ制約でありオリジンの認可を制御しない。
Secrets Managerと対応ローテーション|複数のLambda関数がRDSへ接続する。DBパスワードは定期更新が必要で、ソースコードやビルド成果物へ保存したくない。管理負荷を抑えたい。|Secrets Managerの対応ローテーションと実行ロールによるシークレット取得を利用する。|パスワードをLambdaコードに定数として埋め込む|漏えいリスクと更新時の再配備負荷が増える。|S3公開ファイルへパスワードを書き込む|機密情報保護の要件に反する。|CloudWatchのカスタムメトリクス値としてパスワードを保管する|メトリクスは秘密管理向けではない。
@multi|金融会社は監査ログの管理権限を本番管理者から分離し、保持期間中の削除を防ぎたい。適切な対策を2つ選べ。|ログ集約先の管理境界を分離し、保存先に保持保護を適用する。|1,5|専用監査アカウントのS3へCloudTrail等のログを集約する|本番アカウントの管理権限とログ保管を分離できる。|本番のすべての管理者へログバケットの削除権限を付与する|権限分離に反する。|ログを毎日削除するライフサイクルを設定する|保持義務を満たさない。|CloudTrailを停止する|操作履歴を取得できなくなる。|S3 Object LockのComplianceモードを適切な保持期間で設定する|対応オブジェクト世代を保持期間中の削除から保護する。
AWS WAFのWeb ACL|インターネット向けALB上のECサイトがSQLインジェクションの典型的なHTTP要求を大量に受けている。Webアプリの認可や入力検証に加えて入口で対応する既知パターンを検査したい。|ALBに対応Web ACLとマネージドルール等を関連付けHTTP要求を検査する。|Security Groupのポート443許可だけを設定する|HTTPの内容や攻撃パターンを判定しない。|EBS暗号化を有効にする|保存時暗号化であり受信要求の検査ではない。|Route 53加重ルーティングを設定する|DNS応答の分散はHTTP攻撃の検査にならない。
CognitoユーザープールとAPI認可|新規会員向けWebアプリに登録、ログイン、アクセストークンによるAPIアクセスを提供したい。従業員向けAWS管理コンソールは対象外。|Cognitoユーザープールで会員認証を提供し、APIで対応トークンと認可条件を検証する。|IAMユーザーを会員ごとに作成する|一般利用者向けアプリ認証には不要で権限管理負荷が増える。|Route 53のプライベートホストゾーンを作成する|DNS機能でありユーザー認証ではない。|S3の署名付きURLを会員パスワードとして利用する|会員ID管理・API認可を提供しない。
KMS顧客管理キーとキーポリシー|企業はS3内の機密データの暗号鍵を自社管理し、特定業務ロールの復号だけを許可したい。管理型サービスとの連携と鍵利用の監査が必要。|SSE-KMSで顧客管理キーを使いキーポリシーとIAMで鍵利用を制御する。|SSE-S3のみを使用する|S3管理鍵方式では顧客管理KMS鍵ポリシーを設定できない。|オブジェクトをBase64変換する|符号化であり暗号化ではない。|S3のキー名をランダム化する|保存時暗号化や復号認可の代替ではない。
IAM Identity Center|企業の社員が数十のAWSアカウントに職務に応じた権限でログインする。既存の企業IdPを連携し個別のIAMユーザー管理を避けたい。|Identity Centerと対応外部IdP、permission setによって複数アカウントへのアクセスを一元管理する。|各アカウントに共有rootユーザーを設ける|rootはアカウントごとの強権限主体で共有運用に適さない。|全社員へ一つのS3署名URLを配布する|AWS管理アカウントの認証・認可を提供しない。|全アカウントのVPCをピアリングする|ネットワーク接続とユーザー権限管理は別問題である。
Amazon Macie|データレイクに多数のCSVや文書が集まっている。対応S3オブジェクト内の個人情報候補を検出し、分類結果から調査対象を絞りたい。|Macieの対応データ検出で機密情報を分類する。|AWS Shield Standard|DDoS対策であり保存文書の機密分類ではない。|Amazon Inspector|対応ワークロードの脆弱性検出が主目的である。|VPC Flow Logs|通信メタデータを記録するがS3文書内容を分類しない。
GuardDuty|複数アカウントで異常なAPI利用や不審なネットワーク活動を自動検出したい。既存監視担当へ検出結果を集約する。|対応データソースを利用するGuardDutyの組織運用を構成する。|AWS Budgets|費用閾値通知が主目的で脅威検出を提供しない。|ACM|証明書の発行・管理が主目的である。|AWS Backup|バックアップと復旧の管理サービスである。
プライベートCAによるmTLS|取引先APIへのアクセスにクライアント証明書を要求し、契約先の証明書だけを受け入れる必要がある。対応ALBを使用する。|適切な認証局の証明書と対応ALBのmTLS検証を設定する。|ALBのHTTPリダイレクトのみを設定する|HTTPSへの誘導はクライアント証明書認証ではない。|CloudFrontキャッシュTTLを延長する|配信キャッシュの設定は認証方式を制御しない。|DynamoDBのTTLを設定する|DB項目の期限切れ削除でありクライアント認証ではない。
EKS Pod Identity|EKSの二つのサービスが異なるS3バケットを使用する。ノードロールに両バケットの権限を与えず、Podごとに必要な権限を分離したい。|対応するサービスアカウントとIAMロールのPod Identity関連付けを構成する。|全ノードへ管理者権限を与える|サービス間の権限分離を実現しない。|各Podへ同じ固定アクセスキーを注入する|権限分離と一時認証の利点を失う。|Podの名前をバケット名と同じにする|名前はAWS APIの認可条件にならない。
@multi|データベースは公開IPを持たないRDSで、同一VPCのWebサーバーからのみ接続させる。外部からWebへのHTTPSは許可する。対策を2つ選べ。|公開入口とDBのネットワーク境界を分け、DBへの接続元を限定する。|2,4|DBを公開サブネットに置き0.0.0.0/0からDBポートを許可する|直接外部アクセス禁止に反する。|DBを非公開のDBサブネットグループで公開アクセス不可にする|DBを公開経路から分離する。|WebのSGを全ポートでインターネットに公開する|必要なHTTPS以外も許可するため過剰。|DBのSGでWebサーバーのSGから必要DBポートだけを許可する|許可したWebサーバーを接続元として制限できる。|DBのパスワードをWebの公開ログへ記録する|資格情報を漏えいさせる。
SCPによる予防統制|新規アカウントも含む全開発アカウントで特定リージョン外の対象サービス操作を禁止したい。各管理者が自身のIAMポリシーを変更しても制限を解除できない設計は？|Organizationsの該当OUにSCPを適用して許可の上限を制限する。グローバルサービス等の例外を設計する。|各開発者のIAMユーザーに任意のインラインポリシーを追加する|アカウント管理者が変更できるため中央強制の要件を満たさない。|CloudWatch Logsの保持期間を変更する|操作権限を制御しない。|EC2の起動テンプレートだけを更新する|他のサービスや直接API操作に対するガードレールではない。
S3 presigned PUT URL|モバイル利用者が動画をアップロードする。アプリサーバーに大容量データを通さず、認可した一つのオブジェクトキーに短時間だけ書き込ませたい。|バックエンドで利用者を認可し、指定キー・期限の署名付きPUT URLを発行する。|バケット全体を公開書込みにする|任意主体が書込み可能となり要件に反する。|全利用者に同じ管理者アクセスキーを配布する|過剰権限と長期秘密の漏えいを招く。|動画全体をCognito IDトークンへ埋め込む|IDトークンは大容量オブジェクト転送用ではない。
VPCエンドポイントのインターフェイス型|外部接続を禁止されたプライベートサブネットのEC2が、対応するSecrets Manager APIから資格情報を取得する必要がある。|対応サービスのインターフェイスVPCエンドポイントとSG、プライベートDNS等を構成する。|S3 Gateway EndpointをSecrets Managerにも使う|S3向けエンドポイントはSecrets Manager APIの経路にならない。|EC2へ公開IPを付ける|外部接続禁止に反する。|RDSリードレプリカを作成する|秘密管理APIへのネットワーク接続を提供しない。
IAM Access Analyzer|外部アカウントへ共有されたS3やIAMロール等のアクセス許可を監査し、意図しない信頼境界外アクセスを発見したい。|対応リソースの外部アクセスアナライザーで信頼境界外の許可を検出する。|Amazon Textract|文書解析用でIAMリソースのアクセス分析ではない。|CloudWatch Synthetics|合成HTTPテスト等が主目的でポリシー分析をしない。|EC2 Auto Scaling|計算容量の調整が主目的である。
@multi|アプリのECSタスクはS3を参照し、起動時にはECRイメージ取得とCloudWatch Logs出力が必要。権限を用途別に分離する。適切な対策を2つ選べ。|アプリ用タスクロールと基盤起動用タスク実行ロールを分ける。|1,3|タスクロールにアプリの必要S3操作を付与する|コンテナ内アプリのAWS API認証に利用する。|ECSタスク実行ロールをアプリの管理者ロールとして使う|基盤側の起動処理権限とアプリ権限を分離できない。|タスク実行ロールに必要なECR取得・ログ出力権限を付与する|ECSの対応起動処理に必要となる。|すべてのコンテナへ固定rootキーを設定する|最小権限と短期認証に反する。|S3バケットを公開する|認証済みタスクへの限定アクセスで実現できる。
# 02 レジリエントなアーキテクチャ / 可用性
@multi|Webアプリを単一AZのEC2とRDSで運用している。AZ障害でもサービス提供を継続できる構成が必要。データベースの主系切替は自動化したい。対応を2つ選べ。|計算層を複数AZで提供し、DBに対応Multi-AZ構成を適用する。|1,4|複数AZのAuto ScalingグループをALBのターゲットにする|健全なAZのEC2へ要求を分散できる。|同じAZにEC2を10台増やす|AZ障害という共通故障点を解消しない。|RDSの自動バックアップを停止する|復旧力を損なう。|対応RDS Multi-AZ配置を利用する|AZやDB障害時の対応自動フェイルオーバーを提供する。|S3のバケット名を変更する|WebとDBのAZ障害耐性を改善しない。
SQSと独立したワーカーのAuto Scaling|注文APIが画像変換の完了を同期的に待つためピーク時に受付がタイムアウトする。変換結果は後から取得できる。受付を安定させたい。|SQSに耐久的に登録しAPIは受付を返し、キュー滞留に応じて変換ワーカーを拡張する。|APIサーバーのタイムアウトだけを無制限にする|下流負荷を分離できず接続が滞留する。|処理待ち注文をメモリだけに保存する|インスタンス障害で処理待ちデータが失われ得る。|RDSを単一AZへ変更する|非同期処理の要件を満たさず可用性を低下させる。
SNSと購読者別SQS|一件の決済確定イベントを会計、通知、分析の各サービスで独立処理したい。通知障害で会計処理が遅延してはならない。|SNSでファンアウトしサービスごとにSQSキューを用意する。|一つのSQSキューを三サービスで競合受信する|各イベントが三つのサービスすべてに配送される設計にならない。|会計処理から通知処理のHTTP応答を必ず待つ|障害の影響が連鎖する。|各イベントをEC2のローカルファイルに記録する|サービス間の独立した耐久配送を提供しない。
DynamoDBグローバルテーブル|東京と米国の利用者がそれぞれ低遅延に対応リージョンのキー値データを読み書きする。アプリは選択した整合性モードに対応できる。|対応するグローバルテーブルで複数リージョンへレプリカを配置する。|東京の一つのEBSを米国EC2へ直接アタッチする|EBSは同一AZ接続が前提。|S3 Glacier Deep Archiveへ全要求を書き込む|低遅延のキー値読み書きには適さない。|CloudFrontでDB書込みを永続化する|CDNはDB更新の正本ではない。
Aurora Global Databaseと復旧手順|リレーショナルDBを利用する企業はリージョン災害で数分のRPO、短いRTOを目指す。副リージョンへの継続複製を要する。|対応Aurora Global Databaseを構成して複製遅延を監視しフェイルオーバー手順を検証する。|毎月一回だけS3にCSVを保存する|数分のRPOを満たさない。|同じAZへ読み取りレプリカを追加する|リージョン災害に対応できない。|RDS Proxyを追加するだけ|接続管理でありリージョン間データ復旧ではない。
S3バージョニング|共同編集ツールがS3上の文書を上書きしている。誤って以前の内容を消した際に元バージョンを復元できるようにしたい。|S3バージョニングを有効化して以前のオブジェクト世代を保持する。|S3 Transfer Acceleration|転送高速化であり過去世代を保持しない。|S3のCORS設定|ブラウザのクロスオリジン制約であり履歴管理ではない。|CloudFrontのログ設定|アクセス履歴を記録するが旧文書本体を保存しない。
AWS Backupクロスアカウントコピー|本番アカウントの誤操作や侵害時にも復旧できるよう対応データベースとEBSのバックアップを独立したアカウントに保持したい。|対応するAWS Backupのクロスアカウントコピーと独立したボールト・鍵・権限を構成する。|本番アカウント内の同一管理者が使うボールトだけに保管する|同じ管理境界の侵害で削除されるリスクが残る。|EC2のCloudWatch CPU監視だけを有効にする|復旧データを保管しない。|RDSのリードレプリカを同じアカウント内に置く|誤更新が伝播する可能性があり独立バックアップの代替ではない。
Route 53フェイルオーバールーティング|公開Webサイトに主系と別リージョンの待機サイトがある。DNSによる主系障害時の切替を提供したい。|primary/secondaryのフェイルオーバーレコードと対応正常性評価を構成する。|単純ルーティングで主系だけ登録する|待機側への切替条件がない。|加重ルーティングの重みを固定したまま正常性評価を使わない|障害時に主系への応答を止められない。|S3のライフサイクルで主系のファイルを削除する|DNS切替を提供しない。
EFS Regional|複数AZのLinux EC2が同じPOSIXファイルを同時に読み書きする必要がある。単一AZのファイルサーバーは避けたい。|EFS Regionalを使用し必要AZのマウントターゲットと認可を構成する。|一つのgp3 EBSを複数AZからアタッチする|EBSの接続は同一AZが前提。|EC2インスタンスストアへ保存する|各インスタンスの一時ストレージで共有・永続要件を満たさない。|SQSのメッセージ本文にファイルシステムを保存する|共有POSIXファイルアクセスを提供しない。
@multi|FIFO SQSの注文イベントを処理するLambdaで、同一注文の順序を維持し、処理の再試行で請求を二重実行しないことが必要。対応を2つ選べ。|順序を注文単位で管理し、業務副作用は別途冪等にする。|1,4|注文IDをMessageGroupIdとする|対応するグループ内で順序が維持される。|イベントごとにランダムなMessageGroupIdを作る|同一注文の順序要件を満たさない。|Lambdaのすべてのリトライを禁止する|一時障害への耐性を損なう。|請求IDを一意制約等で管理して副作用を冪等化する|再配信や実行失敗後の再試行による二重処理を防ぐ。|注文IDをログから消去する|順序も冪等性も確保できない。

# 04 コスト最適化アーキテクチャ / 費用設計
