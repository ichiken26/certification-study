# 03 運用・品質 / Glueの再実行と品質
ジョブブックマークを有効にしてjob.commitを呼ぶ|毎晩S3に新着するファイルだけをGlueで処理する。対応するS3ソースを利用しており、前回成功した処理の状態を引き継ぎたい。|ブックマークは処理済みソースの状態を保持し、job.commitで状態を保存する。S3ではオブジェクトの最終更新時刻を利用する。|Crawlerを毎回実行する|メタデータを更新するだけで処理済みファイルを記憶しない。|ジョブの最大同時実行数を1にする|並行実行を抑えるが前回処理した入力を記録しない。|S3のバージョニングを有効にする|オブジェクトの版を保持するがGlueの処理状態は管理しない。
別の出力先に書き込み再処理結果を検証する|Glueブックマークを過去の状態に戻して障害期間のデータを再処理する。元の出力が残っており二重計上を避けたい。|ブックマークの巻き戻しは入力状態に作用し、既存出力を削除しない。別出力や冪等な更新処理を用意する。|ブックマークの巻き戻しだけを行う|出力が自動削除されるわけではなく重複しうる。|Crawlerの実行履歴を削除する|ETL出力とブックマークに影響しない。|S3のストレージクラスを変更する|データの重複を防止しない。
Glueのtransformation_ctxを入力ごとに安定させる|ブックマーク対応DynamicFrameを使うジョブで、入力ソースの状態識別子が毎回変わるように実装したところ差分処理が機能しない。|transformation_ctxはブックマークの状態識別に利用されるため、同一入力について安定した値にする。|実行ごとのUUIDをtransformation_ctxに使う|以前の状態との対応が失われる。|毎回ジョブ名を変更する|ジョブに紐づく状態を継承しない。|出力先の圧縮形式を変更する|状態識別子の問題を解決しない。
DQDLのIsUnique|一意であるべき注文番号の重複をデータ品質チェックで検出したい。|IsUniqueは指定列の値が一意かを検証する。欠損についても別途検証する。|RowCount|行数の検査であり同じ値の重複を直接調べない。|ColumnExists|列の存在確認のみ。|Mean|数値の平均値を評価する。
DQDLのReferentialIntegrity|注文データの顧客IDが顧客マスターに存在することをGlue Data Qualityで検証したい。|参照先データセットとの値の対応をReferentialIntegrityで検査できる。|ColumnCount|列数の検査であり参照整合性を評価しない。|StandardDeviation|数値のばらつきの検査。|IsComplete|NULLの有無を調べるがマスターに存在するかは判定しない。
DQDLのColumnValues|在庫数量は0以上という業務ルールを検証したい。|ColumnValuesで値が許容条件を満たすか評価できる。|ColumnExists|在庫数量列が存在するかだけを評価する。|DatasetMatch|別データセットとの比較用であり単独列の範囲条件を直接表すものではない。|RowCount|行数であり個々の在庫数量を評価しない。
DQDLのRowCountMatch|変換前後で行を追加・削除しない仕様のETLについて、出力件数が入力件数と一致することを検証したい。|RowCountMatchは参照データセットとの行数の比率を比較できる。列値の一致までは保証しない。|ColumnLength|文字列などの長さに関する評価。|ColumnCount|列数のみを比較する。|IsPrimaryKey|キーの一意性と完全性を評価し件数一致を保証しない。
品質エラー行を隔離して正常行と分ける|一部の売上データに不正な日付が含まれている。正常行は取り込み、異常行は後から修正して再投入できる必要がある。|行単位の品質判定結果で分岐し、異常行と原因を隔離ストレージへ保存する。|不正な日付をすべて現在日へ置換する|元データの意味が変わり誤集計につながる。|不正行を無記録で削除する|修正・再投入ができない。|ジョブを成功とみなして全行をそのまま投入する|下流の分析品質を損なう。
# 03 運用・品質 / Redshift
SYS_LOAD_ERROR_DETAIL|Redshift ServerlessへのCOPYが列の変換エラーで失敗した。問題の列やエラー内容を調べたい。|SYS監視ビューはロードエラーの詳細を調べるために利用でき、Serverlessにも対応する。|STL_LOAD_ERRORSだけに依存する|メインのプロビジョンドクラスタ向けでServerlessのロードを網羅しない。|SVV_TABLE_INFO|表のサイズや分布などを調べるビューでロードエラーの詳細ではない。|CloudTrailのCreateClusterイベント|クラスタ作成の監査であり入力列の解析エラーではない。
COPYのNOLOAD|大量のCSVをRedshiftへロードする前に、データ形式が指定した列定義に適合するか確認したい。データの書き込みは行わない。|NOLOADオプションで入力データの妥当性を検証し、実際のロードを行わない。|COPYのTRUNCATECOLUMNS|長い文字列を切り詰める設定であり書き込みを防がない。|UNLOAD|既存データをS3へ出力する操作。|VACUUM|既存テーブルの領域回収やソートなどを行う。
SYS_QUERY_HISTORY|Redshift ServerlessでSQLの実行時間と待ち時間を調べ、遅いクエリを特定したい。|SYS_QUERY_HISTORYはSQLの実行履歴と時間などを確認する監視ビュー。|SYS_LOAD_ERROR_DETAIL|COPY等のロードエラー調査向け。|SVV_TABLE_INFO|テーブルの状態を確認しSQLごとの実行履歴を提供しない。|IAM Access Advisor|AWSサービス権限の使用状況を確認しSQL実行時間は分からない。
WLMクエリモニタリングルールのabort|プロビジョンドRedshiftで過度に長い分析クエリが共有リソースを占有する。特定の実行時間条件を満たしたクエリを終了したい。|クエリ監視ルールの実行時間述語とabortアクションで対象クエリを終了できる。|ルールのlogアクションだけを設定する|監査記録は残るが実行を止めない。|CloudWatchログ保持期間を短縮する|ログ保管設定でSQL実行は止まらない。|テーブルのDISTSTYLEを変更する|データ分布の変更で個々の異常クエリを強制終了しない。
EXPLAIN|Redshiftの結合クエリが大量のノード間データ転送を起こすと疑っている。実際にクエリを実行せず計画を確認したい。|EXPLAINで結合方式やデータ再分配などの推定実行計画を確認する。|ANALYZE|オプティマイザ向け統計情報を更新する操作。|UNLOAD|クエリ結果をS3へ書き出す。|GRANT SELECT|アクセス許可を付与する操作。
ANALYZE|大規模なデータ追加後にRedshiftの実行計画で行数推定が不正確になっている。必要な統計情報を更新したい。|ANALYZEでテーブルや列の統計を更新する。自動分析もあるが必要なら明示実行できる。|VACUUM DELETE ONLY|削除領域を回収するが列統計の更新が主目的ではない。|COPY NOLOAD|外部データのロード前検証。|CREATE USER|DBユーザーの作成。
VACUUM SORT ONLY|Redshiftの表で更新・挿入後にソートされていない範囲が増えた。主にソート順を回復したい。|VACUUM SORT ONLYはテーブルをソートする操作で、DELETE ONLYとは異なる。|ANALYZE|統計を更新するがデータを並べ替えない。|VACUUM DELETE ONLY|削除された行の領域回収が目的でソートしない。|DROP TABLE|データを削除する。
# 03 運用・品質 / ストリーム監視
MillisBehindLatest|Kinesis GetRecordsを直接呼ぶコンシューマーで、取得したレコードがストリームの末尾からどの程度遅れているか判定したい。|GetRecords応答のMillisBehindLatestは最新レコードまでの時間差を示す。0なら末尾に追いついている。|NextShardIterator|次回の取得位置に使う値であり遅延の数値ではない。|PartitionKey|ルーティングに使うキーであり遅延を示さない。|SequenceNumber|レコードの識別と順序に使う値でミリ秒の遅延ではない。
Kinesisのパーティションキーの分散|プロビジョンドKinesisで特定の店舗IDに書き込みが集中し、1シャードだけ書き込み上限に達している。店舗内順序は不要。|より分散するキー設計に変更してホットシャードを回避する。順序要件がある場合は設計を再検討する。|すべてのイベントに同じキーを使う|負荷が1シャードに集中する。|保持期間を延長する|保存期間であり書き込みスループットの分散にはならない。|コンシューマーのログレベルを変更する|プロデューサー側のシャード負荷を解消しない。
PutRecordsのFailedRecordCountと個々の結果を調べる|Kinesisへバッチで投入したAPI呼び出しがHTTP成功を返した。一部レコードがスロットリングで失敗していないか確認する方法は？|応答の失敗件数と各結果のエラーを確認し、失敗レコードだけを再試行する。順序や重複も考慮する。|HTTPステータスだけで全レコード成功と判断する|バッチAPIでは個別レコードが失敗している場合がある。|ストリームの保持期間を確認する|投入結果は分からない。|全レコードを毎回即座に再送する|成功済みレコードの重複や負荷増加につながる。
Enhanced fan-out|独立した3つのコンシューマーが同じKinesisシャードのデータを読み、共有読み取り帯域の競合を避けたい。|登録済みの拡張ファンアウトコンシューマーはシャードごとの専用読み取り帯域を持つ。|全コンシューマーを同じGetRecordsの共有帯域にする|読み取り帯域の競合を避けられない。|S3のTransfer Acceleration|S3転送最適化でKinesis読み取り帯域を変えない。|パーティションキーをすべて固定する|データ分散を悪化させる。
FirehoseのFailedPutCountと応答項目を確認する|アプリからFirehoseへPutRecordBatchで送信する。API呼び出しは成功したが、部分失敗も漏れなく再送したい。|FailedPutCountとRequestResponsesの対応する要素を調べ、失敗分をバックオフ付きで再送する。|DeliveryToS3.Successだけを確認する|下流への配送指標であり今回のバッチ内の個別受付結果ではない。|HTTP成功なら再送しない|失敗レコードを取りこぼす。|毎回新しい配信ストリームを作る|部分失敗の判定を解決しない。
# 04 セキュリティ・ガバナンス / Lake Formation
Lake Formationの列レベルSELECT権限|営業分析担当には売上テーブルの金額と店舗だけを公開し、個人情報の列は参照させたくない。Lake Formationでアクセスを統制している。|許可列に限定したSELECTを付与する。直接S3アクセス等による迂回も防ぐ。|テーブル全列へのSELECTを付与する|個人情報列にもアクセス可能になる。|Glue Crawlerから個人情報の列名だけ隠す|物理データへのアクセス権限は制限されない。|S3のデフォルト暗号化だけを設定する|復号・読み取り権限を持つ利用者の列制御にはならない。
Lake Formationの行フィルター|地域別に同一テーブルの行を制限し、担当者に自分の地域の注文だけをAthenaで参照させたい。|Lake Formationのデータフィルターで行条件を設定してSELECTを付与する。直接のS3権限も制限する。|Athenaのクエリ例にWHEREを記載するだけ|利用者が条件を削除できる。|IAMユーザーの名前を地域名にする|名前の変更だけでは行のアクセス制御にならない。|S3のバージョニング|版管理であり行条件による認可はしない。
LF-Tagsによる権限付与|数百のデータカタログテーブルを機密区分で分類し、分類属性に基づいて分析チームのアクセス権限を管理したい。|LF-TBACはLF-Tag式を用いてリソースに対する権限を付与できる。個別付与の運用負荷を抑えられる。|テーブル名の先頭文字だけでアクセスを自動許可する|命名だけではLake Formationの権限付与にならない。|Glueジョブのブックマーク|ETL処理状態の管理であり認可ではない。|S3のLifecycleルール|保存期間やクラス移行に使う設定。
Lake FormationのSELECT権限と必要なIAM権限を両方付与する|Lake Formation管理テーブルのSELECTを付与したが、分析ロールにlakeformation:GetDataAccessがなくAthenaからデータ取得できない。|Lake Formationのデータ権限に加え、統合サービス利用に必要なIAM権限も付与する。|SELECT権限だけあればすべてのIAM評価を無視できる|統合サービスのIAM許可も必要。|分析ロールにAdministratorAccessを無条件で付与する|必要以上の権限を与える。|Athenaの出力形式をCSVに変更する|認可エラーを解決しない。
リソースリンク|別アカウントからLake Formationで共有されたテーブルをAthenaで参照するため、自アカウントのData Catalogで参照先を表したい。|リソースリンクは共有データベースやテーブルを参照するカタログオブジェクト。リンクと対象の権限を適切に設定する。|S3のオブジェクトタグ|ファイルの属性であり共有カタログへの参照を作らない。|Glueのジョブブックマーク|処理済み入力の記録であり共有テーブル参照ではない。|CloudTrailの証跡|監査ログを記録する。
Lake FormationのDATA_LOCATION_ACCESS|登録されたS3ロケーションを参照する新規カタログテーブルを作成する担当者に、CREATE_TABLEに加えて必要なデータロケーション権限を与えたい。|登録ロケーションに対するDATA_LOCATION_ACCESSは、その場所を指すカタログリソースの作成等に関係する。|SELECTだけを付与する|データの参照権限であり新規テーブルのロケーション権限とは異なる。|DROPだけを付与する|リソース削除権限であり作成権限ではない。|Glue Crawlerのスケジュールを追加する|ロケーションのアクセス許可を与えない。
# 04 セキュリティ・ガバナンス / S3・KMS
S3 Bucket Keys|SSE-KMSの大量オブジェクトを読み書きしてKMSリクエスト費用が増大した。バケット単位のキー利用を許容しSSE-KMSを維持したい。|S3 Bucket KeysはS3とKMS間のリクエストを削減できる。暗号化コンテキストの変更に注意する。|SSE-KMSを解除して平文を保存する|KMSによる暗号化要件を満たさない。|S3のバージョニングを無効にする|KMSの呼び出し削減を直接実現する設定ではない。|CloudTrailのログを削除する|監査記録を失うだけでKMSリクエストを減らさない。
KMSのkms:DecryptとS3のGetObject権限を許可する|SSE-KMSで暗号化されたS3データをGlueが読み取る。実行ロールにはGetObjectがあるが復号権限がない。|S3読み取りとKMS復号の両方の認可が必要。キーポリシー等でも許可する。|kms:GenerateDataKeyだけを付与する|既存データキーの復号に必要な権限の代わりにならない。|s3:ListBucketのみを追加する|オブジェクト列挙権限でありKMS復号はできない。|Crawlerを停止する|暗号化データの認可を修正しない。
S3 Object LockのComplianceモード|監査証跡を7年間、保持期限前にルートユーザーを含む通常の利用者が削除できないよう保護したい。|Complianceモードでは保持期間中に保護対象バージョンの削除や保持期間短縮ができない。|Governanceモードのみ|特権を持つ利用者はガバナンス保持を迂回できる。|S3の通常のバージョニングのみ|版の削除権限を持つ利用者による削除を防がない。|S3 Standard-IAへ移行する|アクセス頻度と料金の設定であり削除保護ではない。
Object LockのLegal Hold|訴訟対応で特定のS3オブジェクトバージョンを期限未定で保全し、対応終了後に権限者が解除したい。|Legal Holdは固定の期限を持たず、適切な権限者が解除するまで保護する。|30日間のCompliance保持だけを設定する|期限が到来すると保護がなくなる。|S3 Lifecycleで30日後に削除する|期限未定の保全要件に反する。|S3のIntelligent-Tiering|ストレージコスト最適化であり法的保全ではない。
Macieの機密データ検出ジョブ|大量のS3ファイルに含まれるクレジットカード番号などの機密データを調査したい。|Macieの機密データ検出で対応ファイルを分析し、検出結果を生成できる。|CloudTrail管理イベント|AWS API操作の記録でありファイル内容の分類はしない。|S3 Storage Lensのみ|ストレージ利用指標を集計するが個々の機密情報を検出しない。|Glueジョブブックマーク|処理済みデータの追跡機能。
CloudTrailのS3データイベント|機密バケット内の個別オブジェクトについて誰がGetObjectを実行したかAPI監査ログで確認したい。|S3オブジェクトレベルのデータイベントを記録するよう設定する。管理イベントのみでは対象外。|CloudTrail管理イベントだけを有効にする|GetObject等のデータ操作は通常の管理イベントに含まれない。|S3の暗号化設定だけを変更する|アクセス履歴を記録する設定ではない。|CloudWatchの請求アラーム|コストを監視するがアクセス主体を示さない。
# 04 セキュリティ・ガバナンス / データの保護
不可逆なトークン化またはハッシュ化と適切な補助対策|本番データから分析用の顧客識別子を作り、元の個人情報を分析者に渡さず同一人物のレコードを結合したい。|一貫した仮名化識別子を作る。推測可能な入力には鍵付きハッシュ等を検討し、再識別リスクを管理する。|氏名と電話番号をそのまま分析表に追加する|不要な個人情報を公開する。|全顧客に同一の固定文字列を割り当てる|同一人物と別人を区別できなくなる。|各行に独立した乱数を割り当てる|同一人物のレコードを結合できなくなる。
データ保持期限をraw・加工済み・バックアップに適用する|個人情報の保存期限が90日と定められた。データレイクのrawだけを90日で消しても集計前の個人情報を含む加工済み表に残る。|データの流れを追跡し、個人情報を含む派生データやバックアップにも保持・削除要件を適用する。|rawだけ削除して完了とする|派生データに個人情報が残る。|すべてをGlacierへ移行する|低価格保存に変わるだけで期限後も残る。|カタログ上の列名だけ変更する|実データは残る。
Secrets Managerとジョブ実行ロール|GlueのJDBC接続で使うDB認証情報をソースコードに埋め込まず、定期的に更新できるようにしたい。|シークレットをSecrets Managerで管理し、取得に必要な権限をジョブに付与する。ローテーション後の接続も検証する。|DBパスワードをETLスクリプトに直書きする|コード共有や履歴から漏洩する可能性がある。|パスワードをCloudWatch Logsへ記録する|監視ログへ秘密情報を漏洩させる。|JDBC接続先をパブリックにする|認証情報管理を改善せず公開リスクを増やす。
S3バケットポリシーでaws:SecureTransportがfalseの要求を拒否|データレイクへのHTTPによる非暗号化リクエストを拒否し、HTTPSを強制したい。|SecureTransport条件の明示的Denyを設定することで非TLSの対象要求を拒否できる。AWSサービス主体への適用条件も確認する。|SSE-KMSだけを有効化する|保存時暗号化であり転送時のTLS強制にはならない。|バケットの名前にhttpsを含める|命名は通信方式を制御しない。|S3のストレージクラスを変更する|料金やアクセス特性の変更でありTLSを強制しない。
