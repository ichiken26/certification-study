# 01 データ取り込み・変換 / DMSの設定
DMSのCDC-onlyタスク|移行先には整合する時点の初期データを別手段で投入済みで、その時点以降の変更だけを反映したい。|CDC-onlyタスクで指定した開始位置以降の変更を取得する。初期データとの開始位置の整合が必要。|Full load only|既存行のコピーのみで継続変更を取得しない。|Full load and CDCで初期投入を無条件にやり直す|既存の初期投入を活用できず重複や置換のおそれがある。|DMSデータ検証のみ|比較を行う機能で変更適用はしない。
ターゲット準備モードのDo nothing|DMSでCDCを開始する前に、移行先の既存テーブルや初期投入済みの行を残したい。|Do nothingはDMSによるターゲットテーブルの削除や切り詰めを行わない。|Drop tables on target|既存表を削除して再作成する。|Truncate|既存表の行を削除する。|Full LOB mode|LOB値の転送方式で表の初期化を制御しない。
DMSのテーブルマッピングのselectionルール|ソースDBのauditスキーマだけを移行対象から除外したい。|selectionルールに対象スキーマとexcludeアクションを指定する。|transformationで列名を変更する|データ構造変更であり対象表の除外ではない。|LOBの最大サイズを0にする|移行対象スキーマを選択しない。|ターゲット準備モードをTruncateにする|対象表の初期化方法であり移行対象の選別ではない。
DMSのtransformationルール|移行先のテーブル名だけを既存命名規約に合わせて変更したい。ソースDBは変更できない。|テーブルマッピングのtransformationルールで対応する名称変更を設定する。|selectionのexcludeだけを設定する|対象表を除外するため移行されない。|CDC開始位置を変更する|取得する変更の位置であり名称変更を行わない。|CloudWatchログレベルを変更する|監視ログの設定である。
Full LOB mode|サイズにばらつきがある大きなLOB列を持つ表をDMSで移行する。LOBを切り詰めずに移行することが必須。|Full LOB modeはLOB全体を転送する。転送性能と対象エンジンの対応条件を確認する。|小さな上限のLimited LOB mode|上限を超えるLOBが切り詰められる可能性がある。|Skip LOB columns|LOBデータの移行を行わない。|ターゲット準備モードのDo nothing|既存表の初期化設定でLOB転送方式ではない。
Limited LOB mode|LOBがすべて32KB以下だと事前検査済み。移行パフォーマンスを優先して上限32KBの設定を使いたい。|Limited LOB modeは既知の最大サイズを指定して効率的に転送できる。上限超過の可能性がないことを検証する。|Full LOB modeだけが選択可能|既知の上限がある場合はLimited LOB modeも使える。|LOB列をすべて削除する|必要なデータを失う。|全表のプライマリキーを削除する|移行やCDCの効率・整合性を悪化させるおそれがある。
DMSのデータ検証|移行完了後にソースとターゲットの対応行に不一致がないか調べたい。対応するDBと表構成を使用している。|DMSのデータ検証で対応行のデータを比較し不一致を報告できる。検証には追加負荷が発生する。|CDCLatencyTargetだけを確認する|適用遅延の指標であり値の一致を保証しない。|ターゲットのCPU使用率だけを確認する|DB負荷を示すがデータ一致は判定できない。|DMSタスクを削除する|検証機能を実行しない。
CDCLatencySource|DMSでソースの変更ログ取得そのものに遅延が生じているか、ターゲット適用遅延と切り分けたい。|CDCLatencySourceでソース変更の捕捉側の遅延を確認する。CDCLatencyTargetと比較して調査する。|FreeStorageSpaceだけ|空きストレージ量でありソース捕捉の遅延を直接示さない。|CDCChangesDiskTargetだけ|ターゲット側のディスクにバッファされた変更数である。|S3 NumberOfObjects|オブジェクト数を表しDMS捕捉遅延とは無関係。
# 02 ストレージ管理 / Athenaの書き込み
AthenaのCTAS|S3上のCSVテーブルを抽出・列選択し、別のParquetテーブルとして保存する。SQLだけでテーブル定義とデータ書き込みを行いたい。|CREATE TABLE AS SELECTはクエリ結果を新規テーブルのデータとして書き出せる。|CREATE VIEW|クエリ定義を保存するだけでデータを物理保存しない。|DESCRIBE|列定義を確認するだけ。|MSCK REPAIR TABLE|既存パーティションの登録を補助する処理でデータ変換はしない。
CTASの出力先を空のプレフィックスに変更する|Athenaでexternal_locationを指定してCTASを実行したら既存ファイルがあるため失敗した。既存ファイルは消さずに新規テーブルを作りたい。|既存ファイルのない出力先を指定する。AthenaはCTASの指定先に残るデータを勝手に上書き・削除しない。|同じプレフィックスでそのまま再実行する|既存データが残っていると問題が解消されない。|SELECTにLIMITを追加する|出力行数を制限しても出力先の既存ファイルは解消されない。|ワークグループ名を変更するだけ|出力先の既存データは残る。
100パーティション以下のCTASと複数回のINSERT INTO|Athenaで300日分のデータを日付パーティションに分けて新規Hive形式のテーブルに書き込みたい。1回のCTASがパーティション上限に達する。|最初に100以下のパーティションを作成し、残りを100以下ずつINSERT INTOする。|CTASで300パーティションを一度に作成する|1回の書き込みパーティション上限に抵触する。|すべてを単一ファイルにして同じCTASを行う|ファイル数を減らしても対象パーティション数は変わらない。|テーブルをVIEWにする|物理的な書き込み要件を満たさない。
INSERT INTOが追加のデータファイルを作成する|AthenaのHive形式Parquetテーブルに10件ずつ毎分INSERT INTOを繰り返したところ読み取り性能が低下した。原因として考えるべきことは？|INSERT INTOは既存ファイルへ追記するのではなく新規ファイルを作成するため、小ファイルが大量に増える。バッチ化や集約を検討する。|INSERT INTOが毎回テーブルを全削除するため|通常のINSERT INTOは既存ファイルを全削除しない。|INSERT INTOが毎回全列を暗号化解除するため|既存データを暗号化解除する動作ではない。|INSERT INTOがGlue Catalogを毎回削除するため|テーブルのメタデータを削除する処理ではない。
Glue Data Catalogのパーティションインデックス|数十万の登録済みパーティションを持つテーブルでAthenaの計画段階が長い。パーティションプロジェクションに適さない不規則な構成である。|パーティションインデックスとAthenaのパーティションフィルタリング設定でメタデータの検索を効率化できる。|S3の転送アクセラレーション|データカタログの検索処理を高速化しない。|SELECTの列にLIMITを追加する|登録済みパーティションの検索効率を直接改善しない。|全パーティションを毎回再登録する|メタデータ処理を増やす。
パーティションプロジェクションでは未登録の投影パーティションがSHOW PARTITIONSに表示されない|Athenaでパーティションプロジェクションを有効にした。SELECTでは対象日付のデータが読めるのにSHOW PARTITIONSにその日付が出ない。|SHOW PARTITIONSは登録済みメタデータを表示する。投影パーティションはクエリ実行時に算出されるため未登録なら表示されない。|データファイルが必ず消失している|SELECTで読み取れているため説明にならない。|プロジェクションはCREATE TABLEにしか対応しない|DMLでパーティションを投影する機能である。|Athenaで日付型を使うこと自体ができない|日付条件は対応している。
# 02 ストレージ管理 / Redshiftの集計
マテリアライズドビュー|Redshiftで毎回同じ大規模な結合と日次集計を繰り返し、結果を事前計算して読み取りを高速化したい。|マテリアライズドビューはクエリ結果を物理保存できる。鮮度を維持するためにリフレッシュを行う。|通常のVIEW|定義を保存するが結果の事前計算を物理保存しない。|CREATE USER|利用者を作る操作で集計結果は保存しない。|GRANT SELECT|アクセス許可の変更でクエリ結果を事前計算しない。
REFRESH MATERIALIZED VIEW|ETLで基表をロードした直後、事前計算済みのRedshiftビューを明示的に更新してからBIに公開したい。|REFRESH MATERIALIZED VIEWで基表の変更をビューへ反映する。完了後に公開処理を進める。|ANALYZEだけ|統計情報を更新するがビューの集計結果は更新しない。|VACUUMだけ|表のソート・領域回収等を行う。|GRANT SELECTだけ|権限を付与するが結果の鮮度は変わらない。
増分リフレッシュ|集計ビューを更新する際に、前回更新後に基表で変化したデータだけを利用して計算コストを抑えるRedshiftの方式は？|対応する定義では増分リフレッシュで変更分を反映できる。SQL定義によっては完全リフレッシュが必要。|完全リフレッシュ|基表を再評価してビュー全体を更新する方式。|データ共有のみ|データ提供の仕組みでビュー更新方式ではない。|COPY NOLOAD|ロード前検証で集計結果を更新しない。
Redshiftのデータ共有|同一リージョンの別チームが独立したRedshiftコンピューティング環境から最新の提供データを参照したい。データの定期コピーは避けたい。|Redshiftのデータ共有でプロデューサーからコンシューマーへデータを共有できる。提供側の変更を参照でき、対応する権限を設定する。|毎日UNLOADしてコンシューマーにCOPYする|データコピーと更新遅延が発生する。|スナップショットを毎日復元する|各環境に復元済みコピーを作るためリアルタイム共有にならない。|クラスターのパスワードを共有する|コンピューティング分離と権限制御の要件に反する。
# 02 ストレージ管理 / S3ライフサイクル
NoncurrentVersionExpiration|バージョニング有効のS3バケットで過去版の保存料金が増えている。最新データは保持し、30日以上経過した非現行版だけを削除したい。|非現行バージョンの有効期限ルールで古い版を削除する。保持ポリシー等との整合が必要。|現行版のExpirationだけを設定する|現行データが非表示になり、旧版の恒久削除とは異なる。|バージョニングを停止するだけ|既存の旧版は自動削除されない。|現行版をStandard-IAへ移行する|非現行版を削除しない。
削除マーカーのバージョンを指定して削除する|バージョニング有効バケットの最新オブジェクトが通常のDELETEで見えなくなった。直前のデータ版は残っている。|削除マーカーのversionIdを指定して削除すれば直前の版を再び現行として参照できる。|同じキーをversionIdなしで再度DELETEする|新たな削除マーカーが作成される可能性がある。|直前のデータ版のversionIdを指定して削除する|復元したいデータそのものを消す。|バケットのバージョニングを停止する|既存削除マーカーを取り除く操作ではない。
AbortIncompleteMultipartUpload|アップロード失敗で残った未完了マルチパートのデータにストレージ料金がかかっている。一定期間後に自動削除したい。|ライフサイクルのAbortIncompleteMultipartUploadで未完了アップロードを中止しパートを削除する。|現行オブジェクトのExpirationのみ|完了済みオブジェクトの期限設定で未完了パートを対象にしない。|S3 Intelligent-Tiering|未完了アップロードを中止しない。|S3 Object Lock|保存対象の版を保護する機能で未完了パート削除ではない。
S3 Batch Replication|レプリケーションルールを新設する前からソースバケットに存在する既存データも複製したい。|S3 Batch Replicationを使い既存の対象オブジェクトを複製できる。通常のライブレプリケーションだけでは既存分を遡及複製しない。|ライブレプリケーションを有効化するだけ|ルール作成前の既存オブジェクトは通常対象外。|バージョニングを停止する|レプリケーションの前提を損なう。|S3 Inventoryだけを有効化する|オブジェクト一覧を生成するが複製は行わない。
ライフサイクルによる削除マーカーはレプリケートされない|S3のソースと宛先で削除マーカーレプリケーションを有効にしている。ソースのLifecycle Expirationが作った削除マーカーも自動複製されるか？|ライフサイクルの期限処理によって作られた削除マーカーは宛先へ複製されない。宛先の保持設定は独立に管理する。|すべての削除マーカーが必ず複製される|ライフサイクルによるものは例外。|宛先のオブジェクト版がすべて永久削除される|削除マーカーの複製と個々の版の永久削除は別。|ソースの暗号化が解除される|削除マーカーの複製とは無関係。
S3 Inventory|数億個のオブジェクトについて定期的にサイズ・ストレージクラス・暗号化状況を一覧化し、Athenaで分析したい。|S3 Inventoryは定期的なオブジェクトメタデータレポートを出力できる。|S3 Select|個々の対応オブジェクト内のデータ検索機能でバケット全体の定期一覧ではない。|S3の署名付きURL|特定操作への期限付きアクセス提供で一覧作成ではない。|S3 Object Lock|版の保持制御でメタデータの定期報告を生成しない。
# 01 データ取り込み・変換 / データ変換とSQL
COALESCE|分析用のSQLで顧客の携帯番号がNULLなら固定電話番号を、両方NULLなら未登録を表示したい。|COALESCEは指定された引数の最初の非NULL値を返す。|NULLIF|2つの値が等しい場合にNULLを返す。|COUNT|件数を集計する。|DISTINCT|重複行を除く。
NULLIFで分母0をNULLにする|売上÷訪問数をSQLで計算する。訪問数0の行でゼロ除算を回避し、結果をNULLにしたい。|売上 / NULLIF(訪問数,0) とすると分母0がNULLとなる。|COALESCE(訪問数,0)で分母を置換する|NULLを0にしてもゼロ除算は回避できない。|ABS(訪問数)を分母にする|0は0のままである。|DISTINCTを指定する|重複排除でゼロ除算は解消しない。
COUNT(*)とCOUNT(列)の差|売上テーブルで行数からメール列の非NULL件数を引き、メールが欠損した行の件数を求めたい。|COUNT(*)は全行、COUNT(email)は非NULL行を数えるので差が欠損数となる。|COUNT(email)-COUNT(*)|欠損行があると負値になる。|COUNT(DISTINCT email)|非NULLの異なる値の数で欠損件数とは異なる。|SUM(email)|文字列の件数やNULL件数を数えない。
HAVING|顧客ID別に購入金額をSUMで集計し、合計が10万円以上の顧客だけを出力したい。|GROUP BY後の集計値への条件はHAVINGで指定する。|WHEREにSUMの条件を記述する|WHEREは集計前の行に作用する。|ORDER BYだけを指定する|並べ替えるだけで条件に合わない行を除外しない。|LIMIT 100000|行数制限で合計値を判定しない。
UNION ALL|同じスキーマの2つの日次売上テーブルを結合して全レコードを保持したい。完全に一致する売上行も別の取引として数える。|UNION ALLは重複を除去せず両方の結果を結合する。|UNION|重複行が除去される。|INNER JOIN|キー等で左右の行を結合する操作で単純な縦結合ではない。|DISTINCT|重複行を除去する。
LAG|日付順に並んだ毎日の売上データに前日の売上値を付け、差分を求めたい。1日1行で欠損日はない。|LAGでウィンドウの前行の値を取得できる。|LEAD|後続行の値を取得する。|ROW_NUMBER|行の順位を生成し前行の売上値を返さない。|COUNT(*)|行数を数える。
