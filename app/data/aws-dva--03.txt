# 01 AWSアプリ開発 / SDKとAPI
SDKのデフォルト認証情報プロバイダーチェーン|ECS上のGoアプリでDynamoDB SDKを利用する。開発PCではSSOプロファイル、本番ではタスクロールの一時認証情報を使い、コードを共通化したい。|SDKのデフォルト認証情報取得機構で環境に応じた認証情報が解決される。ECSではタスクロールの認証情報を利用できる。|本番IAMユーザーのアクセスキーをソースに埋め込む|環境の違いを吸収できず長期キーが漏洩しうる。|ECSのタスク実行ロールをアプリに利用させる|タスク実行ロールはECSエージェント等の処理用。アプリにはタスクロールを使う。|開発PCのSSOキャッシュをコンテナイメージへコピーする|認証情報共有と期限切れの問題を生じる。
SDK paginatorで次ページを反復取得する|AWS SDKのListObjectsV2で最初の1000件だけ取得される。すべてのオブジェクトを列挙する必要がある。|対応SDKのページネーターで継続トークンを管理し結果が尽きるまで取得する。|MaxKeysに100万を指定する|ListObjectsV2の1応答は最大1000件。|同じListObjectsV2リクエストを繰り返す|継続トークンがないと同じページを取得する。|S3バージョニングを有効化する|版の管理であり一覧取得のページングではない。
API GatewayのLambdaプロキシ応答にstatusCodeとbodyを含める|REST APIのLambdaプロキシ統合で関数が通常のJSONオブジェクトだけを返したところ502になった。正しく返すには？|REST APIのLambdaプロキシ統合ではstatusCode、bodyなど所定形式の応答が必要。bodyは文字列として返す。|Lambdaのメモリだけ増やす|レスポンス形式の誤りは解消されない。|CloudWatchログ保持期間を変更する|ログ管理であり応答形式には影響しない。|APIキーを再作成する|認証設定であり応答形式を修正しない。
API Gatewayのマッピングテンプレート|REST APIの非プロキシ統合で、利用者のJSONを既存バックエンドが要求する別のJSON形式へ変換したい。|VTLマッピングテンプレート等でリクエストとレスポンスを変換できる。|APIキーの使用量プラン|使用量を管理する機能で形式を変換しない。|Lambdaの予約済み同時実行数|実行数を制御する機能。|CloudTrailデータイベント|監査記録でHTTP本文変換を行わない。
API Gatewayのステージ変数|REST APIのdevとprodで異なるバックエンドを参照する構成を共通のAPI定義で管理したい。|ステージ変数で環境ごとの統合設定等を参照できる。対応する呼び出し許可も設定する。|レスポンスキャッシュだけを分離する|バックエンド参照先を切り替えない。|Lambdaタイムアウトを環境別に変更する|API統合の呼び出し先は変更されない。|同じ本番URLを両ステージに設定する|devからも本番へ接続してしまう。
# 01 AWSアプリ開発 / ストリーミング
KinesisのPutRecords応答の失敗レコードだけ再送|Kinesisへ複数レコードを送信した。HTTPは成功したが一部のレコードにErrorCodeがある。|PutRecordsはレコードごとに成功・失敗が分かれる。失敗レコードをバックオフ付きで再送する。|HTTP成功だけを見て全件成功とする|失敗レコードを失う。|全レコードを無条件に再送する|成功済みレコードが重複しうる。|GetRecordsで書き込む|読み取り操作で書き込みは行わない。
Kinesis Client Libraryのチェックポイント|Kinesisコンシューマーが再起動した際、最後に処理済みの位置から再開したい。|KCLはチェックポイントで処理位置を管理する。チェックポイント前の再処理を考慮して冪等にする。|ストリームを削除して再作成する|保持済みデータを失う。|すべてのパーティションキーを変更する|処理位置を永続化しない。|DynamoDBのTTLだけ設定する|処理位置を記録しない。
同じ顧客IDをKinesisのパーティションキーにする|同一顧客のイベントを同一シャードに振り分け、異なる顧客は分散したい。|パーティションキーをハッシュしてシャードを決める。同一顧客を同一キーにする。ホットキーや順序制約にも注意。|イベントごとにランダムなキーを付ける|同一顧客のイベントが異なるシャードに分散する。|全顧客に同じ固定キーを付ける|ホットシャードを生じる。|JSON本文に顧客IDを含めるだけ|本文属性はパーティションキーとして自動利用されない。
KinesisイベントソースマッピングのParallelizationFactor|KinesisのLambda処理がシャードごとに滞留している。パーティションキー単位の順序を維持し並行バッチを増やしたい。|ParallelizationFactorでシャード単位の並行バッチ数を増やせる。パーティションキー単位の順序は維持される。|関数のタイムアウトを短くする|並行バッチ数は増えない。|Kinesis保持期間だけを延長する|保持時間は増えるが処理能力は増えない。|Lambdaのエイリアス名を変更する|シャードの処理並列数を制御しない。
# 01 AWSアプリ開発 / S3 API
If-None-Matchにアスタリスクを指定した条件付きPutObject|複数アプリが同じS3キーに書き込む。既存オブジェクトを上書きせず競合を防ぎたい。|If-None-Match: * の条件付き書き込みにより、対象キーに既存の現行オブジェクトがあれば上書きを防ぐ。|HeadObjectで確認して通常のPutObject|確認と書き込みの間に別クライアントが作成できる。|S3 CORSでPUTを許可する|クロスオリジン制御で条件付き作成ではない。|Content-Typeを固定する|形式の宣言で上書きを防がない。
S3 CORSで必要なOriginとMethodを許可|別オリジンのブラウザから署名付きPUT URLへ送信するとプリフライトで拒否される。署名と権限は正しい。|バケットのCORSルールでアプリのOrigin、PUT、必要なヘッダーを許可する。認可とは別。|バケットをパブリック公開する|CORS設定の代替にならず認可を不要に緩和する。|IAMロールに管理者権限を付与する|ブラウザのプリフライト要件を満たさない。|ストレージクラスを変更する|CORSとは無関係。
CreateMultipartUpload、UploadPart、CompleteMultipartUpload|5GBを超えるオブジェクトをS3へアップロードし、失敗した部分だけ再送したい。|開始時のUploadIdを使い各パートをアップロードして完了時にパート情報を渡す。|単一のPutObjectをサイズ制限なしで使う|単一PUTにはサイズ上限がある。|ListObjectsV2で分割ファイルを結合する|一覧APIは結合を行わない。|各パートを同じキーへの独立したPutObjectで保存する|各PUTは上書きでありパート結合をしない。
S3通知のprefixとsuffixフィルター|incoming/配下の.jpgだけサムネイルLambdaに通知し、生成物による再帰実行を防ぎたい。|S3通知のキーフィルターで対象を限定し出力先は対象外にする。|全ObjectCreatedを通知し出力もincoming/へ保存する|生成物も通知対象になり再帰実行しうる。|バージョニングを有効にする|通知対象のキーは制限されない。|予約済み同時実行数を増やす|再帰実行による負荷を解決しない。

強い整合性のGetItem|DynamoDBのベーステーブルに書き込みが成功した直後、別の処理で同じ主キーの最新値を確認したい。|ConsistentReadをtrueにすると強整合性読み取りを利用できる。|GSIへの強整合性Query|GSIでは強整合性読み取りは利用できない。|DAXの結果整合性キャッシュ|最新書き込みの反映を必ず保証する要件に適さない。|ProjectionExpressionだけを設定する|返却属性を絞る機能で整合性は変わらない。

# 02 セキュリティ / 認証と認可
S3バケットポリシーで対象VPCエンドポイント以外のアクセスを拒否する|特定VPC内アプリだけS3にアクセスできるようにし、同じIAM権限があってもインターネット経由は拒否したい。|aws:SourceVpce等の条件で対象外経路を明示的に拒否する。運用アクセスへの影響も確認する。|IAMにGetObject許可だけ設定|接続経路は限定されない。|CORSでVPC CIDRを許可|CORSはブラウザのオリジン制御でVPC経路の認可ではない。|デフォルト暗号化だけ設定|保存時暗号化で経路は制限されない。
STSセッションポリシー|アプリが既存IAMロールをAssumeRoleする際、その一時セッションだけ特定S3プレフィックスに限定したい。|セッションポリシーで元のロールの権限をさらに制限できる。元のロール以上の権限は付与できない。|セッションポリシーで元ロールにない管理権限を追加する|セッションポリシーは権限を拡張できない。|信頼ポリシーをオブジェクト一覧に置き換える|信頼ポリシーは引き受ける主体の制御に使う。|S3ライフサイクルルールを設定する|保存クラスや期限管理であり権限を制限しない。

# 04 トラブルシューティング / 障害調査
実行ロールとKMSキーポリシーのkms:Decryptを確認|LambdaのGetSecretValueでAccessDeniedExceptionが起きる。実行ロールには対象シークレットのGetSecretValueが許可され、顧客管理KMSキーで暗号化されている。|顧客管理キーの復号許可も必要。IAMとキーポリシーの両方を確認する。|タイムアウトを延長する|アクセス拒否は処理時間の不足ではない。|ローテーション周期を短縮する|権限がないまま値を更新しても取得できない。|メモリを増やす|計算資源の増加では認可エラーは解消しない。
CloudWatch Embedded Metric Format|Lambdaの構造化JSONログから注文成功件数と処理時間を個別のPutMetricData呼び出しなしでメトリクス化したい。|EMF形式のログからCloudWatchがメトリクスを抽出できる。高カーディナリティのディメンションによる費用に注意。|CloudTrail管理イベントを記録する|独自アプリの成功件数や時間をメトリクス化しない。|S3タグを追加する|Lambdaログからメトリクスを生成しない。|Lambda環境変数に毎回測定値を保存する|環境変数は設定であり監視の時系列データではない。
API GatewayのIntegrationLatencyとLatencyを比較|APIの応答時間が増えた。バックエンド自体の遅さとAPI Gatewayを含む全体の遅さを切り分けたい。|IntegrationLatencyはバックエンド統合の応答時間、Latencyは要求受信から応答返却まで。差やトレースを確認する。|Countだけ確認する|要求数であり処理時間の内訳は不明。|CloudTrailの呼び出し件数だけ確認する|HTTP要求のレイテンシ分解にならない。|S3の保存容量を確認する|API応答時間とは直接関係しない。
