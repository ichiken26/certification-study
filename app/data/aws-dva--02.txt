# 01 AWSアプリ開発 / APIとイベント
Lambdaの非同期呼び出しとOnFailure Destination|ユーザーの操作に対して即座に受付を返し、Lambdaの実行が再試行後にも失敗した場合は失敗イベントをSQSへ送って調査したい。|非同期呼び出しは受付と実行を分離する。OnFailure Destinationは再試行終了後の失敗レコードをSQS等へ送れる。|Lambdaの同期呼び出しとAPI Gatewayのキャッシュ|同期呼び出しは実行結果を待つ。キャッシュは失敗イベントの保管をしない。|Lambdaのエイリアスと予約済み同時実行数|バージョン選択と並行実行制限であり、最終失敗の配送をしない。|CloudWatch Logsの保持期間を延長する|調査には役立つが失敗イベントをSQSへ送る設定ではない。
API Gatewayのリクエストバリデーター|REST APIで必須のヘッダーやJSONのモデルに不適合な要求を、Lambdaを呼び出す前に拒否したい。|REST APIのリクエスト検証で必須パラメータやモデルを検証できる。Lambda実行回数と不要な処理を削減する。|Lambdaオーソライザーだけを利用する|認証・認可を担当する。通常の入力モデル検証の機能ではない。|レスポンスマッピングテンプレートを設定する|バックエンドの応答を変換する。入力の検証をしない。|API Gatewayのステージキャッシュを有効化する|応答の再利用であり入力モデル検証とは別。
指数バックオフとジッターを伴う再試行|SDK経由のAWS APIが一時的にスロットリングされた。多数のクライアントが同時に再試行して再度スロットリングされないようにしたい。|待機時間を段階的に増やし、ランダムな揺らぎで再試行を分散する。再試行可能なエラーだけを扱い、上限を設ける。|固定1秒間隔で全クライアントを再試行|再試行が同期し、再び負荷集中する可能性がある。|エラー時には待たず無制限に再試行|スロットリングの悪化やコスト増加につながる。|すべてのAWS APIエラーを成功として扱う|実際に失敗した書き込みを成功と誤認する。
イベントIDを永続化し条件付き書き込みで処理済みを判定|SQS Standard経由のポイント付与処理で、同じイベントが再配送されても二重付与しない仕組みが必要。|永続ストアでイベントIDの重複を原子的に判定する。付与処理と判定の整合性も設計する。|Lambdaのグローバル変数にIDを保存|並行する実行環境やコールドスタートで共有されない。|Visibility Timeoutを最大にする|重複配信自体は排除できない。|SQSの保持期間を短縮する|未処理メッセージの消失リスクを増やすだけで重複対策にならない。
SNS購読フィルターポリシー|注文イベントのSNSトピックを共用し、国内注文だけを国内配送キューへ送りたい。購読先アプリでのフィルタリングは避けたい。|SNSの購読フィルターポリシーはメッセージ属性または本文に基づいて購読先への配送を制限できる。|SQS Visibility Timeout|受信後の非表示時間であり配送対象の選別をしない。|SNSトピックの暗号化|保存時暗号化でありメッセージ内容の配送条件ではない。|Lambdaの予約済み同時実行数|関数の同時実行制限でありSNS配送条件ではない。
SQSのChangeMessageVisibility|ワーカーの処理時間が予測できず、受信時のVisibility Timeoutを超えそうになった。まだ処理中のメッセージだけを非表示のまま延長したい。|受信時のReceiptHandleを指定してそのメッセージの非表示時間を変更する。|DeleteMessage|メッセージを削除するため、処理途中で失敗すると再処理できなくなる。|PurgeQueue|キュー内のメッセージをまとめて削除する操作。|SetQueueAttributesのMessageRetentionPeriod|メッセージの保持期間を変更するが受信後の非表示時間の個別延長ではない。
# 01 AWSアプリ開発 / Lambda
VPCのプライベートサブネットにLambdaを接続しRDSのSGで関数のSGを許可|Lambdaから同一VPC内の非公開PostgreSQL RDSに接続したい。DBを公開せずアプリのSGからのみ許可する。|LambdaのVPC接続とSGを構成し、RDS側でそのSGを送信元としてDBポートを許可する。|LambdaにRDSのIAM管理API権限だけを付与する|管理APIの認可だけではDBへのネットワーク経路を確保しない。|RDSをインターネットに公開してIP制限を解除する|非公開と最小権限の要件に反する。|Lambdaのメモリを増加する|計算資源の変更でありVPC接続を提供しない。
NAT Gatewayへの経路を持つプライベートサブネット|VPC接続したLambdaから一般の外部HTTPS APIへ接続したい。IPv4で接続する。|LambdaのENIには通常パブリックIPが付与されないため、外向き経路としてNAT Gateway等を構成する。|Lambdaをパブリックサブネットに配置するだけ|パブリックサブネットに接続してもLambdaにはパブリックIPv4が割り当てられない。|S3 Gateway Endpointだけを配置する|一般の外部HTTPS APIへの経路にはならない。|Lambdaの予約済み同時実行数を増やす|実行枠の設定でありネットワーク接続を解決しない。
SDKクライアントをハンドラーの外で初期化|Lambdaで毎回AWS SDKクライアントを作り直しており初期化処理を減らしたい。実行環境が再利用された場合にクライアントを再利用するには？|ハンドラー外の初期化は実行環境の再利用時に繰り返されない。ユーザー固有の秘密情報や可変状態は安易に共有しない。|ハンドラー内でSDKクライアントを毎回生成する|再利用時にも初期化される。|SDKクライアントのインスタンスをS3へ保存する|実行中のクライアントオブジェクトをS3からそのまま再利用する設計ではない。|SDKクライアントをLambda環境変数へ設定する|環境変数は文字列設定で実行中オブジェクトを保持しない。
予約済み同時実行数|Lambdaから外部のレガシーAPIを呼び出す。関数の同時実行を最大10に制限したい。|予約済み同時実行数10で対象関数の同時実行上限を設定できる。外部APIの厳密なRPS制限は別途考慮する。|プロビジョンド同時実行数10|初期化済み環境を準備する設定であり、それだけでは最大10に制限しない。|関数タイムアウト10秒|個別実行時間の上限で同時実行枠ではない。|関数メモリを10240MBにする|関数の計算資源を増やす設定で同時実行数を制限しない。
ReportBatchItemFailures|SQSイベントソースのLambdaで10件中1件のみ処理失敗した。成功した9件の再実行を避けたい。|部分バッチ応答を有効化し、失敗したメッセージのIDをbatchItemFailuresとして返す。|ハンドラーで未捕捉例外を1つ投げる|バッチ全体が失敗扱いになり成功分も再取得されうる。|失敗したメッセージを含めて正常終了だけを返す|失敗分が成功扱いされ削除される可能性がある。|すべてのメッセージを同じMessageGroupIdに変更する|グループ順序設定であり部分失敗の通知とは別。
Lambdaの/tmp一時ストレージ|LambdaでS3から一時ファイルをダウンロードし、処理後に不要な中間データをローカルファイルとして扱いたい。|/tmpは実行環境固有の一時ファイル領域。容量設定ができ、環境の再利用で残る場合もあるが永続性を前提にしない。|Lambdaの環境変数|文字列設定用であり大きな中間ファイルの保存に適さない。|Lambda Layers|関数と一緒に読み込む依存コード等であり実行中の書き込み先ではない。|関数コードのデプロイパッケージ|実行中の一時データを書き込む場所ではない。
# 01 AWSアプリ開発 / DynamoDB
ConditionExpressionのattribute_not_exists|注文IDが主キーのDynamoDBで、既存注文をPutItemで意図せず上書きしないようにしたい。|条件式attribute_not_existsを主キー属性に適用し、すでに存在する場合は条件付き書き込みを失敗させる。|ProjectionExpressionで主キーを返す|返却属性を指定するだけで上書きを禁止しない。|Scanで存在確認後に条件なしPutItem|確認と書き込みの間に別処理が挿入する競合が発生する。|TTLを注文IDに設定する|期限切れ削除の機能であり重複作成防止ではない。
TransactWriteItems|残高を別々のDynamoDBアイテム間で移動する際、引き落としと入金を全成功または全失敗にしたい。|トランザクションで条件検査と複数アイテムの書き込みを原子的に実行できる。|BatchWriteItem|複数書き込みをまとめるがバッチ全体の原子性はない。|BatchGetItem|複数アイテムの読み取りであり書き込みを行わない。|DynamoDB Streams|事後の変更通知を提供するが書き込みの原子性を保証しない。
UpdateItemでADDを使用|DynamoDBのカウンターを複数ワーカーから並行して増加させたい。各増加要求は一度だけ実行される前提で、読み取り後の上書き競合を避ける。|ADD等による原子的な更新で、GetItem後の値の上書き競合を回避できる。再試行の重複は別途対策する。|GetItemの結果に1を足して条件なしPutItem|同じ値を並行して読み、更新を失う可能性がある。|Scanしてカウンターを取得しPutItem|余分な読み取りと同様の競合がある。|TTLでカウンターを再生成する|期限切れ削除であり原子的増加ではない。
BatchWriteItemのUnprocessedItemsをバックオフ付きで再送|DynamoDBのBatchWriteItemが一部の操作をUnprocessedItemsとして返した。成功済み項目の不要な再送を避けたい。|未処理項目だけを再試行する。スロットリング時は指数バックオフ等を使う。|バッチを全成功とみなして終了する|未処理の書き込みを失う。|すべての書き込みを無条件で即時再送する|成功分の再送やスロットリング悪化につながる。|Scanを実行して未処理項目を自動的に書き込む|Scanは読み取り操作であり未処理書き込みを実行しない。
LastEvaluatedKeyをExclusiveStartKeyへ渡す|DynamoDB Queryの結果にLastEvaluatedKeyがある。続きのページを読みたい。|前回のLastEvaluatedKeyを次回のExclusiveStartKeyとして使用する。キーがなくなるまでページングする。|ProjectionExpressionへLastEvaluatedKeyを設定する|返却属性の指定であり読み取り開始位置ではない。|FilterExpressionでLastEvaluatedKeyより大きい値を指定する|ページングの継続トークンとしての正しい使い方ではない。|同じQueryをパラメータ変更なしで繰り返す|同じページを再度取得する可能性がある。
GSIのパーティションキーをemailにする|userIdが主キーのDynamoDBでメールアドレスによるユーザー検索を頻繁に行う。既存主キーを維持して全件走査を避けたい。|emailをキーとするGlobal Secondary Indexを作りQueryする。GSIは結果整合性であり一意性は別途設計する。|LSIのパーティションキーをemailにする|LSIのパーティションキーはベーステーブルと同じでなければならない。|ScanにFilterExpressionを設定する|絞り込み前にテーブルを読み取るため全件走査を避けられない。|GetItemにemailだけを指定する|GetItemにはベーステーブルの完全な主キーが必要。
# 02 セキュリティ / AWS認証
GitHub ActionsのOIDCとSTS AssumeRoleWithWebIdentity|CI/CDからAWSへデプロイする。GitHubのリポジトリとブランチを制限し長期アクセスキーの保存を避けたい。|AWS側にOIDCプロバイダーと信頼ポリシーを設定し、GitHubのトークンを期限付き認証情報へ交換する。|IAMユーザーのアクセスキーをGitHub Secretsへ保存する|長期キーを保存する要件違反。|AWSアカウントのルートアクセスキーを利用する|必要以上の権限を持つ長期認証情報であり危険。|GitHubのPersonal Access TokenをAWS SDKに渡す|そのトークンはAWS API用の認証情報ではない。
Lambdaの実行ロールとリソースベースポリシーを分離|API GatewayからLambdaを呼び出し、Lambda内のSDKでS3へアクセスする。2種類の権限をそれぞれ設定する方法は？|Lambdaの呼び出し許可をリソースベースポリシーで、関数がS3を操作する許可を実行ロールで設定する。|両方の許可をLambda環境変数に設定する|環境変数はIAMのアクセス許可ではない。|S3へのアクセス許可だけをLambdaのリソースベースポリシーに記述する|実行ロールが持つべきS3操作権限を与えない。|LambdaのSGでS3のAPI権限を許可する|SGはネットワーク通信の制御でAPI認可とは別。
Cognito User PoolのアクセストークンとAPIのスコープ|ログイン済み利用者のAPI操作についてOAuthスコープで認可したい。User Poolを利用している。|アクセストークンにスコープを含め、API側で必要なスコープを検証する。IDトークンは主に利用者の属性等を表す。|IDトークンの表示名だけで操作を許可する|表示名はAPI権限を適切に表さない。|リフレッシュトークンをそのまま各APIへ送る|新しいトークンの取得用であり通常のAPI認可用ではない。|利用者のパスワードをHTTPヘッダーに毎回送る|パスワードの露出を増やしトークンベース認可を行わない。
Cognito Identity Poolで認証結果をIAMロールへマッピング|スマホアプリの認証済みユーザーがAWS SDKで自分専用のS3プレフィックスへアップロードしたい。|Identity Poolは認証済みIDへ一時AWS認証情報を提供する。IAMポリシーで対象プレフィックスへ権限を限定する。|User PoolのJWTをS3のアクセスキーとして使う|User PoolのJWTはS3のSigV4認証情報ではない。|すべての利用者に同一のIAMユーザーキーを配布する|利用者ごとの権限制御と短期認証情報の要件を満たさない。|S3バケットを公開する|第三者にも不要なアクセスを許可する。
IAMポリシーでtenantIdに応じたS3プレフィックスを制限|マルチテナントアプリでテナントごとに同一S3バケットの保存範囲を分ける。認証情報と信頼できるテナント属性はすでにある。|IAM条件やポリシー変数等で認証済みの属性に対応するキー範囲へのアクセスを制限する。API側でもテナント認可を行う。|リクエストURLのtenantIdだけを信用する|利用者が他のテナントIDに変更できる。|全テナントのキーに対するGetObjectを許可する|テナント分離ができない。|S3キーをランダム文字列にするだけ|推測困難性は認可の代わりにならない。
# 02 セキュリティ / 暗号化と機密情報
KMS GenerateDataKeyで生成したデータキーと暗号化済みデータキーを利用|数百MBのデータをアプリ内で暗号化して保存したい。KMSを利用しつつ大きなデータ本体を毎回KMSへ送らない方法は？|平文データキーで本体を暗号化し、KMSで暗号化されたデータキーを一緒に保存する。復号後の平文キーはメモリから適切に破棄する。|KMS Encryptへ数百MB全体を渡す|KMSの直接暗号化には小さなペイロード上限がある。|データキーを平文で本体と同じ場所に保存する|第三者が両方を取得すると復号可能。|KMSのキーIDだけで本体を暗号化する|キーIDは識別子であり暗号鍵の代わりにならない。
Secrets ManagerのAWSCURRENTステージ|ローテーション対応のシークレットからアプリが現在有効な値を取得したい。|GetSecretValueは通常AWSCURRENTステージのバージョンを返す。ローテーション中にはAWSPENDING等が使用される。|AWSPENDINGを常に取得する|検証前の新しいシークレット等を指す場合があり通常の現行値ではない。|AWSPREVIOUSを常に取得する|以前のバージョンを指すため現在有効とは限らない。|シークレットのARNをパスワードとして利用する|ARNはリソース識別子でシークレット値ではない。
Lambda環境変数にはシークレットARNを設定し実行時に取得|DBパスワードのローテーション時にLambdaを再デプロイせず新しい値を取得したい。|環境変数にSecrets Managerの参照先を持たせ、実行ロールで取得する。キャッシュする場合は失効と更新を設計する。|パスワードをLambdaコードに直接記述する|ローテーションごとにコード更新が必要で漏洩リスクもある。|パスワードを平文でCloudWatch Logsへ出力する|ログから秘密情報が漏洩する。|古いパスワードをLambda Layerに固定する|ローテーション後に再パッケージが必要。
S3の署名付きURLを短い有効期限と権限で発行|認証済み利用者に非公開S3の特定オブジェクトだけを期限付きでダウンロードさせたい。|APIが利用者の権限を確認した後、対象オブジェクトに限定した署名付きURLを発行する。|バケットポリシーで匿名GetObjectを許可する|非公開要件に反し全利用者からアクセス可能になる。|IAMユーザーのアクセスキーをブラウザへ渡す|長期認証情報の漏洩リスクがあり対象限定のURLではない。|S3のCORSで対象オブジェクトの認可を行う|CORSはブラウザのクロスオリジン制約でアクセス権限の代替ではない。
# 03 デプロイ / テストとIaC
sam local invoke|SAMで定義したLambdaにサンプルイベントを渡し、ローカルで単一の関数を実行して確認したい。|SAM CLIはDocker等を利用してローカルで関数実行をエミュレートできる。実AWSとの統合は別途検証する。|sam deploy|AWSへスタックをデプロイする。|sam package|デプロイ用成果物をパッケージ化する。|sam validate|SAMテンプレートの構文などを検証するがイベントで関数を実行しない。
sam local start-api|SAMテンプレートのAPI GatewayとLambdaの連携をローカルHTTPサーバー経由で試したい。|ローカルHTTPエンドポイントでAPIをエミュレートできる。|sam local invoke|個別関数のローカル呼び出しでありHTTP APIを待ち受けない。|sam build|関数等のビルド成果物を作る。|sam delete|デプロイ済みスタック等の削除に使う。
CloudFormation Change Set|本番スタック更新でDBが置換されないか確認してから適用したい。|変更セットで追加・変更・削除や置換の可能性をプレビューできる。実行して初めて変更が適用される。|CloudFormation Drift Detectionのみ|現在の実構成とテンプレートの差を検出する機能で次回更新の予測ではない。|CloudFormation StackSets|複数アカウント等への展開を行う機能。|変更内容を確認せずUpdateStack|更新が適用されるため事前確認要件を満たさない。
CloudFormation DeletionPolicy: Retain|CloudFormationスタックを削除しても特定のデータリソースを残したい。|DeletionPolicyのRetainによりスタック削除時に指定リソースを保持できる。更新置換時の保持はUpdateReplacePolicyも考慮する。|DependsOn|リソース間の作成・削除順序の依存を定義する。|Outputs|スタックの出力値を公開する設定。|Parameters|テンプレートへ入力する値を定義する。
CodeBuildのbuildspec.yml|CIで依存関係インストール、テスト、コンパイルと成果物の出力を定義したい。CodeBuildで一般的に利用する設定は？|buildspecのphasesとartifacts等でビルドコマンド・出力を定義する。|CodeDeployのappspec.yml|デプロイ対象やライフサイクルフックを定義する。|CloudFormationのOutputs|スタック出力値でありビルド処理の定義ではない。|IAMの信頼ポリシー|ロールの引き受け条件でありビルドコマンドを定義しない。
CodeDeployのAppSpecとライフサイクルフック|EC2上のアプリをCodeDeployで更新し、配置前後にスクリプトや検証を実行したい。|AppSpecでファイルやライフサイクルイベントのフックを定義する。|CodeBuildのartifactsのみ|成果物の定義でありEC2デプロイ中のフックではない。|CloudWatchのメトリクスフィルター|ログからメトリクスを生成する。|S3のLifecycle設定|ストレージクラス移行や削除などを制御する。
Lambdaエイリアスの重み付きルーティングとCodeDeploy|Lambdaの新バージョンへまず10%の要求を流し、異常時に旧版へ戻したい。|発行済みバージョン間でエイリアスの重みを設定し、CodeDeployのカナリア方式とアラームを用いて移行・ロールバックを自動化できる。|$LATESTのコードを直接上書きして全トラフィックを流す|段階的な公開ではない。|Lambda Layerを削除する|依存ライブラリ管理でありトラフィック分割ではない。|CloudTrailの証跡を無効化する|監査設定でありデプロイ制御ではない。
ECSタスク定義の新リビジョンをサービスへ適用|既存のECSサービスでコンテナイメージのバージョンを変更して段階的に置き換えたい。|新しいタスク定義リビジョンにイメージを指定し、サービス更新でローリングデプロイ等を実行する。|ECRのイメージをアップロードするだけ|既存タスクは自動で新しいイメージに置き換わらない。|ECSクラスターの名前を変更する|実行するコンテナの定義変更ではない。|既存のECSタスク内で手作業でバイナリを更新する|再起動や置換で変更が失われ、再現可能なデプロイにならない。
# 03 デプロイ / AI支援開発
公式仕様とテストで生成コードを検証する|AI支援ツールがAWS SDKのメソッドを提案した。未知のメソッド名で、動作するかは確認されていない。CIに取り込む前に必要な対応は？|利用中のSDKバージョンの公式API仕様を確認し、型検査、単体テスト、必要な統合テストで動作と権限を検証する。|AIが生成したのでSDK仕様は確認せず採用する|存在しないAPIや誤った使い方が含まれうる。|型検査をすべて無効化して通す|誤ったAPIや型の利用を検知できなくなる。|管理者権限を付与して失敗を隠す|権限過剰でありAPIの存在や正しさを保証しない。
合成データと機密値を除いたコンテキストでAIにレビューを依頼|AI支援開発サービスにLambdaコードをレビューさせたいが、コードやログに本番DB認証情報や個人情報が含まれている。|不要な機密情報を除去し、組織で承認されたツールとデータ取り扱い設定を使用する。検出・レビュー・テストを併用する。|本番の秘密情報をそのままプロンプトに含める|認証情報や個人情報の不必要な外部送信となる。|本番DBを公開してAIに直接読み取らせる|データ公開の範囲を広げる必要がない。|レビュー用ツールに全AWSアカウントの管理者権限を付ける|レビュー目的に対して過剰権限となる。
Bedrock RuntimeのConverse API|対応する複数の基盤モデルに対し、一貫したメッセージ形式で会話型アプリを実装したい。|Converse APIは対応モデルへ共通のメッセージ形式でリクエストできる。モデルごとの対応機能は確認する。|SageMakerのTraining Job API|モデルの学習ジョブを実行するAPIで会話推論用ではない。|Amazon TranscribeのStartTranscriptionJob|音声の文字起こし処理を開始する。|Amazon TranslateのTranslateText|テキスト翻訳用で汎用的な会話型基盤モデル呼び出しではない。
Bedrock Guardrails|生成AIアプリで禁止トピックや機密情報等に関するガードレールを設定し、対応モデルの入力・出力を評価したい。|Guardrailsは設定したポリシーでコンテンツの評価・制御を支援する。アプリの認可や安全性検証も必要。|Lambdaの予約済み同時実行数|同時実行数を制御するだけでコンテンツを評価しない。|S3のBlock Public Access|S3公開の制御であり生成AIコンテンツの評価ではない。|CloudFrontのキャッシュポリシー|キャッシュキーやTTLを管理しAIの応答内容を評価しない。
# 04 トラブルシューティング / 可観測性
CloudWatch Lambda Throttlesメトリクス|Lambdaの一部要求が同時実行上限で受け付けられない。関数のスロットリング件数を監視する標準メトリクスは？|Throttlesは同時実行制限等によるスロットリングされた呼び出し回数を表す。|Duration|実行時間を表しスロットリング件数ではない。|Errors|関数実行のエラー数でありスロットリング件数とは別。|ConcurrentExecutions|同時実行数であり拒否された呼び出し回数ではない。
CloudWatch Lambda IteratorAge|KinesisからLambdaへイベントを処理している。関数が処理するストリームレコードがどの程度古くなっているか監視したい。|IteratorAgeは処理されるストリームレコードの経過時間を表す。バックログや処理遅延の兆候として利用できる。|Lambda Duration|個別関数の実行時間でレコードの古さではない。|Lambda Errors|関数の実行エラー数。|SQS NumberOfMessagesDeleted|SQSから削除したメッセージ数でありKinesisの遅延指標ではない。
SQS ApproximateAgeOfOldestMessage|動画変換キューで一番古い未削除メッセージがどれくらい待たされているか監視したい。|最古メッセージの概算経過時間を用いて処理滞留を検知できる。指標の仕様上例外もある。|SQS NumberOfMessagesSent|送信件数で待機時間を表さない。|Lambda Duration|関数の実行時間でキュー待機時間ではない。|SQS NumberOfEmptyReceives|空の受信要求数を表す。
相関IDを構造化ログへ記録しサービス間で伝播|API Gateway、Lambda、SQSワーカーをまたいで1つの注文処理のログを追跡したい。|要求IDや注文処理IDを各サービスに渡し、構造化ログの同じフィールドへ出力して検索する。|すべての処理で新しい無関係なIDを生成する|処理の関連付けが難しくなる。|デバッグログをすべて無効化する|必要な調査情報が不足する。|利用者の生パスワードを相関IDにする|秘密情報がログに漏洩する。
CloudWatch Logs Insightsのフィールド抽出・集計|JSONログのstatusCodeごとにエラー発生件数を集計したい。既存ログから即時調査する。|Logs Insightsのクエリでフィールドのフィルタやstats count等による集計ができる。|CloudTrailの管理イベントのみを検索する|アプリケーションのHTTP応答ログとは別。|S3のObject Lockを有効化する|保存データの保持保護でありログ集計機能ではない。|Lambdaのエイリアスを切り替える|バージョン制御であり既存ログの集計ではない。
# 04 トラブルシューティング / 最適化
Lambdaのメモリ割当を複数値でベンチマークする|CPU律速のLambdaのDurationが長い。実行コストも抑えながら最適なメモリ設定を決めたい。|CPU配分はメモリに連動する。メモリを増やすと実行時間が短縮してGB秒課金も下がる場合があるため実測比較する。|最小メモリを必ず選ぶ|実行時間が長くなり総コストが下がらない場合がある。|最大メモリを必ず選ぶ|性能改善が頭打ちになる場合もあるため最小コストとは限らない。|タイムアウトを短くするだけ|処理性能は改善せず途中終了する可能性がある。
RDS Proxy|多数のLambda実行環境が短時間でPostgreSQLの接続を開き、最大接続数に達する。SQLの変更を避けたい。|RDS ProxyがDB接続をプールし再利用する。トランザクションやセッション状態によるピン留めなども考慮する。|DynamoDB DAX|DynamoDB専用キャッシュでPostgreSQLの接続管理はしない。|CloudFront|HTTPキャッシュでありDBコネクションをプールしない。|RDSのスナップショットを増やす|バックアップを増やしても接続枯渇は改善しない。
DynamoDB Queryと適切なGSIを利用|DynamoDBテーブルを毎回Scanして顧客IDで絞り込んでいるため、レイテンシと読み取り費用が増加している。顧客IDは主キーではない。|顧客IDを検索キーとするインデックスを用意しQueryで必要な項目にアクセスする。GSIの書き込み費用も考慮する。|ScanのFilterExpressionをさらに追加する|読み取り後にフィルターするためスキャン範囲は減らない。|テーブルのTTLだけを短縮する|必要データを失う可能性があり検索パターンを改善しない。|ProjectionExpressionだけで読み取り容量を必ず減らす|返却属性の制限は項目の読み取り容量を直接減らさない。
SQSイベントソースの最大同時実行数を設定|同一Lambdaに複数のSQSキューを接続している。特定キューだけが関数の実行枠を使い尽くさないよう制限したい。|対応イベントソースマッピングのMaximumConcurrencyでキューごとの同時実行数を制御できる。関数予約枠との整合も取る。|関数のメモリ割当を変更する|キューごとの並行処理上限は設定されない。|SQSのDelaySecondsを一律に増やす|初回取得可能になるまでの遅延であり同時実行上限ではない。|関数のログ保持日数を短縮する|実行枠の配分には影響しない。
