# 01 IAM・基礎 / 認証と権限
IAMロール|EC2上のSDKからS3へアクセスしたい。長期アクセスキーを持たずに権限を付与するには？|EC2のインスタンスプロファイル経由でロールを付与すると、SDKが期限付き認証情報を取得・更新できる。
IAMユーザー|外部システムの互換性上、AWSの長期アクセスキーを発行する必要がある。どのIAM主体が直接キーを持てるか？|IAMユーザーにはアクセスキーを発行できる。ただし通常はロールによる一時認証情報を優先する。
IAM Identity Center|社員が複数AWSアカウントへ企業IdPでSSOし、権限セットを割り当てたい。|複数アカウントの人間向けアクセスを一元管理する。個別IAMユーザーを大量に作る必要がない。
AWS STS|信頼された別アカウントのロールを引き受け、短時間だけAPIを操作するために利用する認証サービスは？|AssumeRoleで一時的なアクセスキー、秘密キー、セッショントークンを取得する。
# 01 IAM・基礎 / ポリシー
SCP|組織のメンバーアカウントで、管理者権限を持つユーザーにも特定リージョンの利用を原則禁止したい。|SCPはOrganizationsで利用する権限の上限。許可を付与するものではなく、メンバーアカウントの権限を制約する。
アクセス許可境界|開発者にIAMロールを作らせるが、そのロールに付けられる有効な権限の上限を制限したい。|Permissions boundaryはIAMエンティティのアイデンティティベースポリシーが付与できる最大権限を定義する。
リソースベースポリシー|S3バケットそのものに、別アカウントの特定ロールを許可する設定を付けたい。|バケットポリシーはリソース側にPrincipalを指定できる。クロスアカウントでは通常、呼び出し側の許可も必要。
ロールの信頼ポリシー|あるIAMロールをどのサービスやアカウントが引き受けられるか指定するには？|信頼ポリシーはAssumeRoleを許可する主体を定義する。引き受けた後に実行可能な操作とは別。
# 01 IAM・基礎 / 評価
明示的Denyが優先される|同一リクエストに有効なAllowと明示的Denyが存在する。評価結果は？|AWSのポリシー評価では該当する明示的拒否が許可に優先する。
暗黙的Denyになる|IAMユーザーに対し対象操作の許可も明示的拒否も存在しない。評価結果は？|デフォルトは拒否。操作を許可するポリシーが必要。
SCPだけでは許可されない|SCPでEC2の操作が許可範囲にあるが、IAM主体に操作の許可がない。実行できるか？|SCPは許可の上限にすぎないため、別途IAM等で権限を付与する必要がある。
ルートユーザーを日常利用しない|AWSアカウント作成後、通常の管理作業のセキュリティを高めたい。推奨する運用は？|ルートユーザーは必要な作業だけに限定しMFAを設定する。通常は適切な権限のフェデレーション等を使う。
# 02 ネットワーク / VPC
Internet Gateway|パブリックIPv4を持つEC2をインターネットに接続するため、サブネットのデフォルトルートの宛先にするものは？|IGWをVPCに接続しルートを設定する。IPv4の場合はパブリックIPと通信許可も必要。
NAT Gateway|パブリックIPのないIPv4 EC2からインターネットへパッケージを取得したい。外部からの新規接続は不要。|パブリックNAT Gatewayを使い、プライベートサブネットの外向き通信を変換する。
Gateway VPC Endpoint|同一リージョンのS3への通信がNAT Gatewayのデータ処理料金を発生させる。追加のエンドポイント料金なしで接続したい。|S3またはDynamoDB向けルートを追加する。Gateway型は時間料金・データ処理料金がない。
Interface VPC Endpoint|プライベートサブネットからSecrets ManagerのAPIにインターネットなしで接続したい。|PrivateLinkによるENIにプライベートIPでアクセスする。Secrets ManagerはInterface型を利用する。
Egress-only Internet Gateway|IPv6のEC2から外部へ通信したいが、インターネットからの新規接続は禁止したい。|IPv6向けの外向き通信とその戻りを許可するゲートウェイ。IPv4のNATとは異なる。
# 02 ネットワーク / 通信制御
Security Group|EC2のENI単位で、送信元ALBからのTCP 8080だけを許可したい。応答通信は自動許可したい。|SGはステートフルで許可ルールのみ。ALBのSGを送信元に指定できる。
Network ACL|サブネット境界で特定のIP範囲を明示的に拒否し、ルール番号順に評価したい。|NACLはステートレスで許可・拒否がある。戻り通信の許可も必要。
ルートテーブル|宛先CIDRに応じてNAT Gatewayや別VPCへの次の経路を選択したい。|ルートテーブルは最長プレフィックス一致などで転送先を決める。ポート単位の許可とは異なる。
VPC Flow Logs|ENIに対するネットワークフローの送信元・宛先・ACCEPT/REJECTを確認したい。|IPトラフィックのメタデータを記録する。パケット本文のキャプチャではない。
# 02 ネットワーク / 接続
VPC Peering|重複しないCIDRの2つのVPCをプライベートIPで直接接続したい。推移的ルーティングは不要。|1対1接続でルートを設定する。CIDR重複不可、推移的ルーティング不可。
Transit Gateway|多数のVPCとオンプレミスをハブに集約し、ルート管理を簡素化したい。|VPCやVPNを接続するルーティングハブ。個別のPeeringのメッシュを避けられる。
AWS PrivateLink|別アカウントの特定サービスだけをプライベート公開したい。VPC全体の双方向接続は不要でCIDRも重複する。|サービス単位の接続で消費側にENIを作る。VPC全体のルーティングは不要。
Site-to-Site VPN|オンプレミスのルーターからAWSへの暗号化されたIPsec接続を短期間で確立したい。|インターネット上のIPsecトンネルを利用する。専用線の開通を待つ必要がない。
Direct Connect|オンプレミスとAWS間にインターネットを経由しない専用接続を確保したい。|専用またはホスト型接続を利用できる。通信の暗号化は別途要件に応じて検討する。
Client VPN|個々の社員のPCからVPCにVPN接続させたい。|クライアント端末向けのマネージドVPN。拠点間接続とは異なる。
# 02 ネットワーク / DNSと配信
Route 53 Latency-based routing|東京と米国にサービスを展開し、DNS応答で利用者のレイテンシが低いリージョンへ誘導したい。|AWSが測定するレイテンシを基にリージョンを選択する。
Route 53 Failover routing|通常は東京のエンドポイントを返し、異常時には大阪の待機系をDNSで返したい。|ヘルスチェック等と組み合わせてプライマリからセカンダリへ切り替える。
Route 53 Weighted routing|新バージョンへDNSレベルで概ね10%のトラフィックを段階的に流したい。|レコードに重みを付与する。DNSキャッシュがあるためHTTPリクエスト単位の厳密な割合ではない。
Route 53 Geolocation routing|利用者の国・地域に応じて言語別のサイトへDNSで案内したい。|利用者の地理的位置を基に応答先を選ぶ。
CloudFront|静的画像やHTTPコンテンツをエッジにキャッシュしてオリジンへのアクセスを削減したい。|CDNとしてエッジでキャッシュでき、TLSやWAFとも連携する。
Global Accelerator|世界中のTCP/UDPクライアントに固定Anycast IPを提供し、AWSのネットワーク経由で最適なエンドポイントへ誘導したい。|固定IPとAWSバックボーンを活用する。HTTPコンテンツのキャッシュは行わない。
# 03 コンピューティング / EC2購入方式
On-Demand|稼働時間が予測できない短期の実験環境で中断は許容できない。期間契約も不要。|使用量に応じて課金され、長期コミットメントを必要としない。
Spot|途中中断されても再開できる大量のバッチ処理を、空きキャパシティで安く実行したい。|余剰キャパシティを割安に利用するが、中断される可能性がある。
Compute Savings Plans|1年継続のコンピュート利用額を約束し、EC2のファミリー変更やLambda、Fargateへの移行にも割引を適用したい。|時間あたりの利用額のコミットメントで、対象サービス・構成の柔軟性が高い。
Dedicated Host|物理ホスト単位のソフトウェアライセンスを持ち込むため、ホストの割り当てを管理したい。|専有物理サーバーの可視性と配置制御を提供する。
# 03 コンピューティング / 負荷分散
ALB|同じHTTPSの入口から /api と /images を別々のターゲットグループに振り分けたい。|L7のHTTP情報を用いてパスやホストによるルーティングが可能。
NLB|TCP/UDPのサービスで固定IPを利用し、高いスループットのL4ロードバランサーが必要。|L4でTCP/UDP/TLSなどを扱う。AZごとに固定IPを持つ。
GWLB|仮想ファイアウォール製品を複数台で運用し、ネットワークトラフィックを透過的に検査したい。|GENEVEを用いて仮想ネットワークアプライアンスにトラフィックを分散する。
Auto Scaling Group|CPU使用率を目標値に保つため、EC2の台数を自動で増減したい。|起動テンプレートとスケーリングポリシーによりEC2の容量を管理する。トラフィック分配はELB等が担当する。
# 03 コンピューティング / 実行環境
ECS|AWSネイティブのコンテナオーケストレーターで、タスク定義とサービスを使ってコンテナを維持したい。|ECSはコンテナの配置・維持を管理する。EC2またはFargateを実行基盤にできる。
EKS|既存のKubernetesマニフェストを活かし、KubernetesコントロールプレーンをAWSに管理させたい。|マネージドKubernetes。ノードの方式は別途選べる。
Fargate|ECSのコンテナを実行する際、EC2の台数・パッチ・OSを管理したくない。どのコンピュート方式を使うか？|コンテナのサーバーレス実行基盤。ECS/EKSなどのオーケストレーションとは役割が違う。
ECR|DockerイメージをAWS内のプライベートレジストリに保存し、ECSからpullしたい。|コンテナイメージの保管・配布を担当する。
AWS Batch|多数の独立したバッチジョブをキューに登録し、依存関係やコンピュート容量を管理して処理したい。|バッチジョブのスケジューリングと実行環境の管理に適する。
Elastic Beanstalk|Webアプリのソースをデプロイし、EC2やELB等の環境構築を自動化したいが基盤の設定にもアクセスしたい。|Webアプリの環境を自動構成するPaaS型サービス。基盤リソースは利用者のアカウントに作成される。
# 03 コンピューティング / 配置
Cluster Placement Group|同一AZでHPCのノード間通信遅延を抑え、高いネットワークスループットを得たい。|インスタンスを近接配置する。単一AZの障害には弱くなる。
Spread Placement Group|少数の重要なEC2を異なる物理ハードウェアに配置し、同一機器障害の影響を減らしたい。|個々のインスタンスを分離する配置戦略。
Partition Placement Group|大規模なHadoop等の分散システムで、複数の論理パーティションが別々のラック群を使うようにしたい。|パーティション間でハードウェアを分離する。大規模な分散ワークロード向け。
複数AZのAuto Scaling Group|物理ラック障害だけでなくAZ全体の障害にも備え、Webサーバーを自動補充したい。|AZをまたいで容量を維持する。単なる配置グループではAZ障害時の補充は管理しない。
# 04 ストレージ / 種類
S3|数百万の画像をオブジェクトキーとHTTP APIで扱い、サーバーにディスクをマウントせず保存したい。|オブジェクトストレージ。通常のブロックデバイスやPOSIX共有ディスクとは異なる。
EBS|EC2のLinuxルートディスクとして、永続的なブロックデバイスが必要。|AZ単位のブロックストレージ。別AZに直接アタッチはできない。
EFS|複数AZのLinux EC2からNFSで同じファイルを共有したい。|Regional EFSは複数AZにまたがる共有ファイルシステム。
Instance Store|EC2停止時に消えてもよいキャッシュ用のホストローカルディスクが欲しい。|インスタンスに物理的に接続した一時ストレージ。停止・終了等でデータが失われる。
FSx for Windows File Server|WindowsアプリでSMBとActive Directory統合を利用した共有ファイルサーバーを構築したい。|Windows向けのマネージドファイルシステム。
FSx for Lustre|HPCのLinuxジョブからS3データを利用し、高速な並列ファイルシステムで処理したい。|Lustreは計算処理向けの高性能共有ファイルシステム。S3との統合が可能。
# 04 ストレージ / S3クラス
S3 Standard|毎日頻繁に読み書きするデータを、複数AZで即時取得可能に保存したい。|頻繁にアクセスする汎用ストレージ。取り出し料金はないが保存単価は低頻度向けより高い。
S3 Intelligent-Tiering|アクセス頻度が予測不能な長期データを、アクセスパターンに応じて自動的に階層移動させたい。|アクセス状況に応じた階層移動を自動化する。対象オブジェクトには監視料金などがある。
S3 Standard-IA|月に数回参照する重要データを複数AZで保持し、ミリ秒で読み出したい。アーカイブ階層は不要。|低頻度向けで取り出し料金があり、最低保存期間は30日。
S3 One Zone-IA|再生成可能な副次データを低頻度で読み、単一AZ消失を許容してStandard-IAより保存費を抑えたい。|単一AZ保存。重要な原本には通常不適切。
S3 Glacier Instant Retrieval|四半期に一度程度読むアーカイブでミリ秒取得が必須。低い保存単価を優先する。|低頻度アーカイブで即時取得可能。最低保存期間は90日。
S3 Glacier Flexible Retrieval|長期保管データを通常数時間以内に復元したい。Deep Archiveほど長い待ち時間は許容しない。|復元操作が必要なアーカイブ。標準取得は通常3〜5時間。
S3 Glacier Deep Archive|7年間保管するほぼ読まない監査データで、通常12〜48時間の復元待ちを許容し保存費を最小化したい。|長期アーカイブ向けで保存単価が低い。最低保存期間は180日。
# 04 ストレージ / S3機能
バージョニング|オブジェクトを誤って上書きした場合に過去の版へ戻したい。|同じキーの複数バージョンを保持する。削除マーカーにも注意。
Object Lock Complianceモード|監査データを一定期間、ルートユーザーを含めて変更・削除できないようにしたい。|WORM保護。Complianceモードでは保持期間中に削除や短縮を行えない。
Cross-Region Replication|新規S3オブジェクトを別リージョンのバケットへ自動的に複製したい。|CRRは別リージョンへの非同期複製。送信元・先のバージョニング等を設定する。
ライフサイクルルール|作成後30日のオブジェクトを低頻度向けへ移行し、365日後に自動削除したい。|オブジェクトの年齢等に応じて移行・期限切れを自動化する。
署名付きURL|匿名のブラウザに、限定時間だけ非公開S3オブジェクトのダウンロードを許可したい。|署名者の権限内で時間制限付きアクセスを提供する。バケット公開は不要。
Multipart Upload|巨大なオブジェクトのアップロードを複数パートに分け、失敗したパートだけ再送したい。|並列送信や部分再送が可能。未完了のパートを削除する運用も必要。
Transfer Acceleration|遠隔地の利用者から単一S3バケットへの長距離アップロードをエッジ経由で高速化したい。|エッジロケーションを経由してAWSネットワークを活用する。
# 04 ストレージ / EBS
gp3|一般的なEC2のOS・アプリ用ディスクで容量とIOPS/スループットを独立して調整したい。|汎用SSD。規定範囲内で容量に依存せず性能を設定できる。
io2|高いIOPSと高耐久性を要求する重要DB向けに、プロビジョンドIOPS SSDを選びたい。|高性能・高耐久性が必要なブロックワークロード向け。
st1|頻繁に大きなファイルを順次読み書きする分析用データディスクで、HDDのスループットを重視したい。|スループット最適化HDD。小さなランダムI/Oや起動ディスクには適さない。
sc1|アクセス頻度の低い大容量の順次読み書きデータで、EBS HDDの単価を抑えたい。|Cold HDD。低頻度の大容量データ向けで起動ディスクには利用できない。
EBSスナップショット|AZ-AのEBS内容を保持し、同一リージョンのAZ-Bで新しいボリュームを作りたい。|スナップショットから対象AZに新規EBSを復元できる。元ボリュームの直接アタッチとは異なる。
# 05 データベース / RDS・Aurora
RDS Multi-AZ DBインスタンス|PostgreSQLの読み取り負荷は問題ないが、AZ障害に備え同期スタンバイへの自動フェイルオーバーが必要。|別AZに待機系を持つ従来型Multi-AZ。スタンバイは読み取り用ではない。
RDS Read Replica|RDSのプライマリが大量のSELECTで高負荷。非同期複製の遅延を許容して読み取りを分散したい。|読み取り用レプリカを作り、アプリから参照先を分離する。
RDS Proxy|多数のLambdaが短時間にDB接続を開き、接続数が枯渇する。SQLは変更したくない。|DB接続をプール・再利用して接続集中を緩和する。クエリ結果キャッシュではない。
Aurora Serverless v2|MySQL互換DBで負荷が大きく変動するため、DB計算容量を細かく自動調整したい。|Auroraのコンピュート容量をACUで自動スケールする。エンジン等の条件により挙動は異なる。
Aurora Global Database|Auroraを別リージョンへ低遅延で複製し、リージョン規模の障害対策と海外からの読み取りに利用したい。|クロスリージョンのストレージベース複製を利用する。
Point-in-time recovery|RDSで誤ってDELETEした時刻の直前へ、別DBインスタンスとして復元したい。|自動バックアップとログから保存期間内の特定時刻へ復元する。
# 05 データベース / NoSQLとキャッシュ
DynamoDB|キーで取得する大量のユーザーセッションを、サーバー管理なしで低遅延のNoSQLに保存したい。|キーバリュー・ドキュメント型。アクセスパターンに合わせたキー設計が重要。
DynamoDB DAX|DynamoDBの結果整合性の読み取りを大量に処理するため、マイクロ秒級の専用インメモリキャッシュが欲しい。|DynamoDB API互換のキャッシュ。強整合性読み取りはキャッシュされない。
ElastiCache|PostgreSQLの検索結果やセッションをRedis互換のインメモリデータ構造にキャッシュしたい。|Valkey/Redis OSSやMemcachedを利用できる。DB負荷を低減する。
DynamoDB Streams|DynamoDBのアイテム変更を時系列のストリームとして取得し、Lambdaで処理したい。|変更レコードを最大24時間保持する。テーブル全体の定期Scanは不要。
DynamoDB Global Tables|複数リージョンから同じDynamoDBテーブルを読み書きし、リージョン間の複製を管理させたい。|マルチリージョンのテーブル複製。整合性モード等の制約は別途確認する。
DynamoDB TTL|期限が切れたセッションアイテムを、アプリで一括削除せず最終的に自動削除したい。|期限属性で自動削除する。指定時刻ちょうどの削除は保証されない。
# 05 データベース / データモデル
Amazon Redshift|大規模な構造化データを列指向のデータウェアハウスで集計・BI分析したい。|OLAP向け。行単位の頻繁なトランザクション処理とは用途が異なる。
Amazon Neptune|人物間の関係や経路をグラフ構造として保存し探索したい。|グラフDB。複雑な関係性を探索する用途に向く。
Amazon DocumentDB|MongoDB互換APIを使うドキュメント型DBをマネージドサービスで利用したい。|MongoDB互換のドキュメントDB。完全互換ではないため機能差は確認する。
Amazon Keyspaces|Apache Cassandra互換のワイドカラムDBをサーバーレスで使いたい。|Cassandra互換のマネージドデータベース。
# 06 非同期・サーバーレス / メッセージ
SQS Standard|多数のワーカーで独立したジョブを処理し、順序は不要で重複を許容する。高い処理能力が必要。|少なくとも1回の配信とベストエフォート順序。冪等なコンシューマーが必要。
SQS FIFO|注文ごとのイベント順をメッセージグループ内で維持し、送信重複排除も利用したい。|グループ単位の順序と送信重複排除を提供する。処理の冪等性も考慮する。
SNS|単一の通知を複数の独立した購読者へ同時に配信したい。|Pub/Subでfan-outする。購読先をSQSにすれば各処理が独立する。
EventBridge|複数サービスのイベント内容をルールのパターンで照合して対象システムへ配送したい。|イベントバスとルールを利用する。イベントの送信元と処理先を疎結合にする。
Kinesis Data Streams|連続的なログを保持し、複数のコンシューマーが独立した位置から再読できるようにしたい。|保持期間内にストリームを再読できる。シャードやオンデマンド容量を利用する。
Amazon MQ|既存のJMS/AMQP等のメッセージブローカーをアプリの変更を抑えてAWSへ移行したい。|ActiveMQやRabbitMQのマネージドブローカー。SQSへの書き換えを避けたい用途に適する。
# 06 非同期・サーバーレス / SQS操作
Visibility Timeout|ワーカーが受信したメッセージを処理中だけ他のワーカーから一時的に見えなくしたい。|受信後の非表示期間。削除されなければ再び取得可能になる。
Dead-letter queue|何度再処理しても失敗するメッセージを通常キューから隔離して調査したい。|maxReceiveCountを超えたメッセージをDLQに送るようredrive policyを設定する。
Long polling|空のSQSキューを繰り返し問い合わせる無駄なAPIリクエストを削減したい。|メッセージ到着まで最大20秒待つReceiveMessageを利用できる。
Message retention period|コンシューマーが長期間停止した場合、未処理メッセージをキューに保存する期間を調整したい。|メッセージの保持期間を指定する。処理中の一時非表示時間とは異なる。
# 06 非同期・サーバーレス / 実行・連携
Lambda|S3への画像アップロードをきっかけに数秒のサムネイル処理を、サーバー管理なしで実行したい。|イベント起動の関数実行。1回の実行上限は15分。
Step Functions|複数の処理の分岐、待機、リトライ、実行状態を宣言的に管理したい。|ステートマシンでワークフローをオーケストレーションする。
API Gateway|Lambdaの前にHTTP APIを公開し、ルートや認証、スロットリングを管理したい。|マネージドAPIの入口。関数実行やデータ永続化は別サービスが担当する。
EventBridge Scheduler|毎朝9時にLambdaを起動するスケジュールを、タイムゾーン指定で管理したい。|単発・定期実行のスケジュールを管理する。イベントの内容によるルーティングとは異なる。
# 07 セキュリティ・運用 / 暗号化と秘密
AWS KMS|暗号化に使用する鍵をマネージドで管理し、鍵の利用権限や監査を制御したい。|データキーを保護するエンベロープ暗号化等を利用できる。
Secrets Manager|RDSのパスワードをアプリ外で管理し、自動ローテーションさせたい。|シークレットの保存と対応するローテーション機構を提供する。
SSM Parameter Store|アプリの設定値を階層化した名前で保存し、必要に応じSecureStringで暗号化したい。自動ローテーションは不要。|設定情報の一元管理に向く。SecureStringはKMSを利用する。
ACM|ALBにHTTPSの公開TLS証明書を設定し、適切な条件で更新を自動化したい。|AWS Certificate Managerが証明書を発行・管理する。
CloudHSM|専有HSM上の鍵を自社で制御し、HSM固有のコンプライアンス要件を満たしたい。|専用ハードウェアセキュリティモジュールを利用する。KMSより利用者側の管理が多い。
# 07 セキュリティ・運用 / 検知と保護
AWS WAF|HTTPリクエストのSQLインジェクションや特定パターンをルールで遮断したい。|L7のWeb ACLでHTTPリクエストを検査する。
AWS Shield|ネットワーク・トランスポート層のDDoSからAWS公開サービスを保護したい。|Shield Standardは対象AWSサービスに自動適用される。Advancedは追加の保護・支援を提供する。
GuardDuty|CloudTrail等のデータソースから不審なAPI操作や侵害の兆候を検出したい。|脅威検知サービス。構成変更の監査記録そのものとは異なる。
Inspector|EC2やECRイメージ等のソフトウェア脆弱性を継続的に検出したい。|脆弱性管理サービス。パッケージ等の既知脆弱性をスキャンする。
Macie|S3バケットに保存された個人情報や機密データを発見したい。|S3データの分類・機密情報検出を行う。
Security Hub|複数セキュリティサービスの検出結果を集約してセキュリティ態勢を評価したい。|検出結果やセキュリティ標準の評価を一元化する。
# 07 セキュリティ・運用 / 監視
CloudWatch|EC2のCPUメトリクスが閾値を超えたときにアラームを発生させたい。|メトリクス、ログ、アラームの監視サービス。
CloudTrail|誰がいつEC2を終了するAWS APIを呼んだか確認したい。|AWS API等のアクティビティを記録する。監査に利用する。
AWS Config|S3バケット等のリソース構成履歴を記録し、組織の設定ルールに準拠しているか評価したい。|構成の記録・ルール評価を行う。
AWS X-Ray|マイクロサービスをまたぐリクエストの分散トレースで遅延箇所を調べたい。|トレース情報を用いてサービス間の依存と処理時間を可視化する。
Systems Manager Session Manager|EC2への管理接続でSSHのインバウンドポートや踏み台を開けずにシェルへ接続したい。|SSM Agent、IAM権限、必要な接続経路を使う管理セッション。
CloudFormation|VPCやEC2等のインフラ構成をテンプレートとして宣言し、スタックで管理したい。|Infrastructure as Codeとしてリソースを作成・更新する。
# 08 DR・コスト / 復旧
Backup and Restore|DR用の稼働環境は維持せず、障害時にバックアップからデータとシステムを復元する。最も低コストな一般的戦略は？|平時の稼働資源は少ないが、復旧に時間がかかる傾向がある。
Pilot Light|DR側で中核データと必要最小限の機能を維持し、障害時に残りのアプリを起動する戦略は？|中核部分だけを準備する。平時にフル機能のシステムは動いていない。
Warm Standby|DR側で本番と同じ機能を持つ縮小環境を常時稼働し、障害時に増強する戦略は？|縮小された完全な環境を維持するためPilot Lightより早い復旧を目指せる。
Multi-site Active-Active|複数リージョンが平時から本番トラフィックを受け、片方の障害時にも残りが処理する戦略は？|複数の本番環境を同時稼働する。高コストでデータ整合性設計も重要。
# 08 DR・コスト / 費用管理
AWS Budgets|月のAWS費用が設定した予算の80%に達した場合に通知したい。|予算と実績・予測に基づくアラートを設定する。通知だけでは利用を停止しない。
Cost Explorer|過去の費用をサービス・タグ・期間で集計し、費用の変化や予測を可視化したい。|コストと使用量の分析ツール。
Compute Optimizer|EC2等の利用メトリクスから過剰なインスタンスサイズの推奨変更を知りたい。|利用状況に基づいてリソース構成の最適化を提案する。
AWS Backup|複数の対応サービスのバックアップポリシー・保持期間を一元管理したい。|バックアップ計画と保管を管理する。バックアップだけでは即時フェイルオーバーはできない。
# 09 周辺サービス / 分析
Athena|S3のParquetファイルをサーバー管理なしでSQL検索したい。|S3上のデータをSQLで直接分析する。スキャン量の削減が費用改善につながる。

Amazon Data Firehose|ストリーミングデータをバッファリング・変換し、S3等の保存先に継続的に配信したい。|マネージド配信サービス。コンシューマー自身が任意位置から読むストリームとは異なる。
OpenSearch Service|ログの全文検索やインデックスに基づく検索を高速化したい。|全文検索・分析エンジンをマネージドで運用できる。
