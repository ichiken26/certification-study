# 04 セキュリティ・ガバナンス / データ保護
S3バケットポリシーでaws:SecureTransportがfalseの場合に明示的Deny|データレイクのS3へのHTTPアクセスを、IAMで許可済みの利用者も含めて禁止したい。|TLSを使わない要求を明示的に拒否することで、他のAllowより優先できる。|S3のデフォルト暗号化だけを設定|保存時暗号化でありHTTPを拒否しない。|IAMのAllowにGetObjectを追加|HTTP通信を禁止しない。|S3バージョニングを有効化|オブジェクトの履歴を保持する機能。
SSE-KMSとKMSキーポリシー|データレイクの保存時暗号化に使用する鍵を自社で管理し、鍵利用権限をデータアクセス権限と分離したい。|カスタマー管理KMSキーを使用し、キーとS3の権限を適切に管理する。|SSE-S3のみ|S3管理鍵を使用するため指定したKMSキーの利用権限を管理できない。|HTTPSのみ|転送中の暗号化であり保存時の鍵管理ではない。|S3アクセスログ|アクセス記録であり暗号化機能ではない。
S3 Bucket Keys|SSE-KMSで暗号化した多数の小さなS3オブジェクトに対するKMSリクエスト費用を削減したい。|S3 Bucket KeysはS3からKMSへのリクエスト数を削減できる。暗号化コンテキストの変更にも注意する。|S3 Transfer Acceleration|長距離転送を高速化する機能。|S3 Object Lock|削除や上書きから保護する機能。|S3 Inventory|オブジェクトの一覧を定期出力する機能。
Lake Formationの列レベル権限|分析担当者に顧客テーブルの売上列だけを公開し、住所列の参照を禁止したい。AthenaとLake Formationを利用する。|対応するテーブルに列単位のSELECT権限を設定する。S3への直接アクセスによる迂回も防止する。|S3プレフィックスの権限だけで同一Parquet内の列を制限|S3はファイル内の列をIAMで区別しない。|Athenaの結果保存先を変更|元データの列権限を制限しない。|Glueクローラーの実行頻度を減らす|メタデータ更新頻度であり認可ではない。
Lake Formationのデータフィルター|同じテーブルに全地域の売上がある。地域担当者には担当地域の行のみをAthenaで公開したい。|対応するデータフィルターで行条件を指定しSELECT権限を付与する。|S3のライフサイクルルール|保存期間やストレージクラスを制御する。|Glueのテーブル説明に地域名を記載|説明はアクセス制御を強制しない。|AthenaのSQL履歴を削除|クエリ履歴の扱いであり行認可ではない。
Amazon Macie|S3の大量のファイルから個人情報の可能性があるデータを発見して分類したい。|Macieは対応するS3オブジェクトを分析し機密データの検出を支援する。|CloudWatch Metrics|数値指標を監視するがファイル内の個人情報を分類しない。|AWS DMS|データベースの移行や複製を行う。|AWS Backup|バックアップ管理を行うが機密データの分類はしない。
CloudTrailのS3データイベント|特定のS3バケットで誰がGetObjectを実行したかAPI操作の監査記録を残したい。|対象バケットのオブジェクトレベルのデータイベントを有効にする。通常の管理イベントだけでは不足する。|CloudTrail管理イベントのみ|GetObjectはオブジェクトレベルのデータイベント。|S3ストレージクラス分析|アクセス傾向の分析であり利用者別API監査ではない。|Glueジョブブックマーク|ETLの処理状態を管理する。
S3 Object LockのComplianceモード|法令で定められた保持期限まで、アカウントのルートユーザーでも監査オブジェクトのバージョンを削除できないようにしたい。|Complianceモードでは保持期限内の保護対象バージョンの削除や保持期間短縮ができない。|Governanceモードのみ|特別な権限を持つ利用者は保護を迂回できる。|S3バージョニングのみ|権限を持つ利用者は特定バージョンを削除できる。|S3 Intelligent-Tiering|アクセス頻度に応じた階層化であり削除禁止ではない。
Secrets ManagerとGlue接続|Glueジョブで外部DBの認証情報を使用する。コードへの平文埋め込みを避け、ローテーション可能にしたい。|Secrets Managerに認証情報を保存し、対応する接続設定とジョブロールに取得権限を付与する。|Glueスクリプトにパスワードを記述|コードから秘密情報が漏れる可能性がある。|CloudWatchログに認証情報を保存|ログ閲覧者への漏洩リスクがある。|S3オブジェクト名にパスワードを含める|オブジェクト名が秘密情報の保護手段にはならない。
Redshiftの動的データマスキング|同一テーブルの電話番号を一般分析担当者には伏せ字、許可された担当者には元の値で表示したい。|動的データマスキングポリシーをロール等に適用しクエリ時の表示を制御する。|Redshiftの分散キーを電話番号にする|行の分散配置を制御するだけ。|VACUUMを実行|テーブルの整理であり表示制御ではない。|COPYで同じデータを再ロード|ロード操作だけでは利用者別マスキングを実現しない。
# 01 データ取り込み・変換 / ストリーミング
Kinesisのパーティションキーの分散|全イベントに同じパーティションキーを指定した結果、他シャードに余裕があるのに書き込みがスロットリングされる。順序保証は顧客単位でよい。|顧客IDなど十分に分散するキーを選び、同じ顧客のイベントは同じキーにする。|全イベントのキーを固定したままシャード数だけ増やす|単一キーへの集中は解消しない。|保持期間を延長|再読可能期間は増えるが書き込み分散は改善しない。|コンシューマーの数を減らす|書き込み側のキー偏りを解決しない。
Kinesis Enhanced Fan-Out|複数の独立したコンシューマーが同じストリームを低遅延で読み、共有読み取り帯域の競合を避けたい。|登録コンシューマーごとの専用読み取りスループットを利用できる。|S3 Glacier Deep Archive|長期アーカイブ用ストレージでリアルタイム読取に適さない。|Kinesisの保持期間延長|履歴の保持期間を増やすが専用帯域は提供しない。|Firehoseのバッファ時間延長|配送をまとめる設定で低遅延の独立読み取りを提供しない。
Kinesis PutRecordsの失敗レコードのみ再送|バッチ送信のHTTP応答が成功でもFailedRecordCountが正数だった。データ欠落を避けたい。|各レコードの結果を確認し、失敗したものをバックオフ付きで再送する。|HTTP成功だけで全レコード成功と判定|個別の書き込み失敗を見逃す。|成功レコードのみ再送|失敗分が欠落する。|保持期間を延長して終了|未書き込みレコードは保持されない。
Firehoseの動的パーティショニング|JSONイベントをS3へ配送する際、イベント内の地域属性に応じてプレフィックスを分けたい。|動的パーティショニングで抽出したキーに応じてS3プレフィックスを構成する。|S3バージョニング|同じキーの履歴を保持する機能。|KMSキーのローテーション|暗号鍵管理であり配送先の分類ではない。|Athenaの結果出力先変更|Firehoseの配送先を制御しない。
Firehoseのレコード形式変換|JSONのイベントをS3にParquetとして保存し、別途Sparkジョブを運用したくない。|対応する形式変換を有効にしGlue Data Catalogのスキーマを指定する。|S3のストレージクラス変更|ファイル内容の形式は変換されない。|CloudTrailのデータイベント|監査ログを記録するだけ。|Kinesisのシャード分割|ストリーム容量を調整するが形式変換はしない。
DMSのフルロードとCDC|稼働中のDBを移行する。既存行をコピーした後、切替まで発生する変更も取り込みたい。|フルロードと継続的変更複製を組み合わせる。ソースのログ設定等も確認する。|CDCのみで空のターゲットを開始|既存の変更されない行が欠落する。|フルロードのみ|ロード後の変更を追従しない。|Glueクローラーのみ|スキーマを検出するがデータを複製しない。
# 02 ストレージ管理 / クエリとテーブル
Athenaのパーティションプロジェクション|日付プレフィックスが規則的に増えるS3テーブルで、毎日のパーティション登録作業を省きたい。|パーティション値とパスの規則をテーブルプロパティで定義し、Athenaに計算させる。|毎回CREATE DATABASEを実行|データベース作成でありパーティションの自動計算ではない。|S3 Object Lock|オブジェクト保護でありメタデータ登録を省かない。|RedshiftのVACUUM|Redshift内部テーブルの整理でありAthenaの機能ではない。
Athenaワークグループのクエリ単位スキャン上限|分析者の誤った全件スキャンで費用が膨らむ。単一クエリの読み取り量を制限したい。|ワークグループにクエリ単位のデータ使用量制限を設定し、超過クエリを停止できる。|S3のバージョニング|オブジェクト履歴を管理するだけ。|Athenaの結果再利用だけ|再利用できない新規クエリのスキャンを制限しない。|Glueクローラーを停止|既存テーブルへのクエリは制限されない。
Redshift COPYで複数ファイルを並列ロード|大量のS3データをRedshiftに取り込む際、単一巨大ファイルの逐次処理を避けたい。|適切に分割した複数ファイルをCOPYでロードし並列処理を活用する。|1行ずつINSERTする|多数のSQL実行オーバーヘッドが生じる。|UNLOADを使用|Redshiftから外部へデータを出力する操作。|VACUUMのみ実行|既存データを整理する操作でロードはしない。
Redshift UNLOAD|Redshiftの集計結果をS3へParquet形式で出力して別の分析基盤から利用したい。|UNLOADでSELECT結果をS3へ出力でき、Parquet形式も指定できる。|COPY|S3等からRedshiftへ取り込む操作。|ANALYZE|統計情報を更新する操作。|TRUNCATE|テーブルの行を削除する操作。
# 03 運用・品質 / 障害調査
Step FunctionsのRetryとCatch|ETLワークフローで一時的なAPIエラーは再試行し、回復不能な失敗は通知処理へ分岐したい。|Retryで対象エラーと再試行条件を指定し、Catchで失敗時の遷移先を定義する。|すべてのタスクを無条件に成功扱い|データ欠落や処理失敗を隠してしまう。|S3の保持期間延長|ワークフローのエラー分岐を定義しない。|Glueクローラーの分類器を追加|データ形式検出であり再試行制御ではない。
DMSのCDCLatencyTarget|DMSでソース側の変更取得は進んでいるがターゲットへの適用が遅れている疑いがある。どの指標を確認するか。|CDCLatencyTargetをCDCLatencySourceと比較しターゲット側の適用遅延を調査する。|S3 BucketSizeBytes|S3の容量でありCDC適用遅延ではない。|Lambda Duration|Lambdaの実行時間でありDMSの複製遅延ではない。|Athenaのスキャン量|SQLの読み取り量でありDMSの遅延を示さない。
Glue Data QualityのUniquenessルール|注文データの注文IDについて重複がないことを品質検査で確認したい。|Uniquenessで指定列の一意性を評価できる。|Completenessのみ|NULL等の欠損を評価するが重複は検出しない。|RowCountのみ|行数が同じでも重複が存在しうる。|ColumnExistsのみ|列の存在を確認するだけ。
