# 04 セキュリティ・ネットワーク / IAMとコンプライアンス
IAMポリシーシミュレーター|IAMロールに複数のポリシーを付与している。実際の削除APIを呼び出さず、特定のS3操作に対するポリシー評価を調査したい。|シミュレーターで対象アクション・リソース等についてポリシーの評価を試せる。実環境の全条件を再現するとは限らない。|CloudTrailの証跡を削除する|監査情報を失い権限の評価はできない。|IAMロールに管理者権限を付与する|元の権限状態が変わり調査にならない。|S3 Inventoryを実行する|オブジェクト一覧の作成でIAM評価とは別。
IAM Access Analyzerの外部アクセス分析|社内AWSアカウントを信頼境界とし、S3バケットポリシーなどから境界外の主体にアクセスが許可されているリソースを発見したい。|外部アクセス分析は対応するリソースポリシー等を解析して信頼ゾーン外からのアクセスを検出する。|IAMのパスワードポリシー|ユーザーのパスワード要件で外部共有を分析しない。|AWS Backupの復元テスト|バックアップの復元検証。|CloudWatchのCPUアラーム|CPU使用率の監視。
IAM Access Analyzerのポリシー生成|実行ロールが実際に使用したAWS APIの履歴を基に、より限定的なポリシーのたたき台を作りたい。|CloudTrailのアクティビティから使用権限に基づくポリシーを生成する機能がある。必要な未使用操作もレビューする。|すべてのIAMアクションを許可する|最小権限に近づかない。|SGのアウトバウンドを制限するだけ|ネットワーク制御でありIAM操作の生成ではない。|AWS Configの記録を停止する|ポリシー生成を実現しない。
OrganizationsのSCP|開発アカウントのIAM管理者が許可を追加しても、特定のサービス操作を組織として禁止したい。対象はメンバーアカウントの通常IAM主体。|SCPはメンバーアカウントの利用可能な権限の上限を制限する。明示的DenyはIAMのAllowより優先される。|IAMユーザーの名前を変更|権限評価を制限しない。|Cost allocation tag|費用分類用のタグ。|VPCルートテーブルだけを設定|AWS APIの組織横断認可を制御しない。
SCPのAllowに加えてIAM側のAllowが必要|メンバーアカウントに適用されるSCPがs3:GetObjectを許可しているが、対象IAMロールにS3の許可がない。SCPだけで読み取れるか？|SCPは許可の上限でありアクセス権そのものを付与しない。通常は適切なIAMまたはリソースベースの許可が必要。|SCPだけで常に読み取れる|SCPを権限付与ポリシーと混同している。|SCPがAllowならバケットの明示的Denyを無視できる|明示的Denyは優先される。|S3バケットをパブリックにする必要がある|適切な権限を付与すれば公開は不要。
IAM Identity Centerのpermission set|複数のAWSアカウントに所属する社員へ共通の閲覧権限を割り当て、ログインを統合したい。|権限セットを作成しグループとアカウントに割り当てることで、対応するロールと権限を管理できる。|アカウントごとに同じ長期アクセスキーを配布する|認証情報の管理を分散させる。|S3アクセスポイントを作成|S3のアクセス管理で複数アカウントの社員ログインを統合しない。|CloudWatchダッシュボードを共有する|観測画面共有に限られAWSアクセス権の統合ではない。
IAM permissions boundary|開発者にIAMロール作成を委任するが、作成するロールが特定権限範囲を超えないようにしたい。境界を付けること自体もIAM条件で強制する。|permissions boundaryは対象ロールのアイデンティティベース権限の上限を設定する。委任側には境界の強制も必要。|ロールのセッション名だけ制限|操作権限の上限を設定しない。|ロール名にdevを付ける|名称だけで権限範囲は制限されない。|CloudTrailのログを暗号化|監査ログ保護であり権限の委任制限ではない。
IAM信頼ポリシー|別アカウントの指定されたロールにだけ自アカウントの運用ロールを引き受けさせたい。引き受け元の主体を制限する設定は？|信頼ポリシーのPrincipalと条件でAssumeRoleを許可する主体を定義する。呼び出し側の権限も必要に応じて設定する。|運用ロールの許可ポリシーだけ|引き受け後の操作範囲を設定するもので信頼主体の指定ではない。|SGの送信元にアカウントIDを記載|SGはIAMロールの信頼設定ではない。|CloudWatchアラームの通知先を指定|認証主体を制限しない。
AWS Configのコンフォーマンスパック|監査基準に対応する複数のConfigルールと修復設定を一括で複数アカウントに展開したい。|コンフォーマンスパックはルールと修復アクションをまとめて管理・展開できる。|CloudTrailのイベントセレクター|監査対象APIを選択する設定で構成評価ルールを展開しない。|S3 Lifecycle|保存期間とストレージクラスの管理。|IAMアクセスキーのローテーション|認証情報の管理で監査ルールの展開ではない。
AWS Configのアグリゲーター|複数アカウント・リージョンのConfigの構成情報と準拠状態を管理アカウントから参照したい。|アグリゲーターはソースから構成・コンプライアンス情報を集約する。ルールを自動配布する機能とは別。|コンフォーマンスパックだけ作成|ルール配布用であり集約ビューとは異なる。|VPC Transit Gateway|ネットワーク接続を集約するがConfigのデータは集約しない。|各アカウントで同じタグを設定|統合ビューは作られない。
AWS Configの自動修復とSSM Automation|未準拠のリソースに対して、承認済みのSSM runbookを自動実行し構成を修正したい。|Configルールに修復アクションを関連付けて自動修復を設定できる。実行権限・再試行・例外の設計が必要。|Configの記録だけ有効化する|記録だけでは自動修正しない。|CloudTrailのログをS3へ保存するだけ|操作記録のみで修正処理を実行しない。|CloudWatchダッシュボードを作る|可視化だけで修復は行わない。
Amazon Inspector|EC2やECRの対応イメージ等のソフトウェア脆弱性を継続的に検出したい。|Inspectorは対応するワークロードの脆弱性を検出する。|Amazon Macie|主にS3データの機密情報発見。|AWS Backup|バックアップの管理。|Route 53 Resolver|DNS名前解決を提供する。
Amazon GuardDuty|AWS環境のAPIやネットワーク関連のデータなどから不審な挙動を検出したい。|GuardDutyは対応するデータソースを分析し脅威の検出結果を作成する。|AWS Budgets|費用や使用量を監視する。|S3 Inventory|オブジェクトの一覧出力。|AWS Artifact|コンプライアンス文書等の入手。
AWS Security Hub|複数のセキュリティサービスの検出結果を集約し、共通のセキュリティ基準への準拠状況を確認したい。|Security Hubの対応機能で検出結果やセキュリティ状態を一元管理できる。|S3 Transfer Acceleration|S3の転送を最適化する。|EC2 Auto Scaling|インスタンス台数を調整する。|Route 53の重み付きルーティング|DNS応答割合の制御。
# 04 セキュリティ・ネットワーク / 暗号化・秘密情報
KMSキーポリシーとIAM許可|暗号化したEBSボリュームの操作がKMS AccessDeniedで失敗する。IAMにKMS許可を追加したがキーポリシーでその許可を使用できる設定がない。|KMSのキーポリシーやグラントとIAMを含めて必要な権限を評価する。IAMの許可だけで解決しない場合がある。|SGでKMSポートを開くだけ|認可エラーはネットワークルールだけでは解消しない。|EBSの容量を増やす|暗号鍵の権限に影響しない。|CloudWatchログを削除|KMSのアクセス権を変更しない。
KMSキーを無効化して利用影響を検証|顧客管理KMSキーの廃止を検討している。不可逆な削除の前に、暗号化済みデータへのアクセス影響を確認したい。|キーを無効化すると対応する暗号操作が失敗しうる。必要に応じて再有効化できるので依存関係を検証できる。|即時にキー素材を完全消去する|元に戻せずデータ復号ができなくなるおそれがある。|キーのエイリアス名だけ変更する|キーIDによる利用を停止しない。|CloudTrailの証跡を停止|キーの利用を制限しない。
ACMのDNS検証用CNAMEを保持|ALBに設定したACMのDNS検証済み公開証明書を自動更新したい。証明書は対象サービスで使用中である。|DNS検証レコードを保持し、自動更新の条件を満たす。レコードの削除は更新失敗につながる。|証明書発行後に検証レコードを削除する|以後のDNS検証が失敗する可能性がある。|ALBのHTTPリスナーを削除するだけ|証明書更新条件を維持する設定ではない。|ACMの証明書ARNを毎日変更する|自動更新の仕組みではない。
CloudFront用ACM証明書をus-east-1で発行|東京リージョンのACMにある公開証明書をCloudFrontのビューアー向けカスタムドメインに設定できない。|CloudFrontのビューアー証明書としてACMを使う場合、米国東部バージニア北部リージョンの証明書を用意する。|任意のリージョンのACM証明書を直接指定|CloudFrontのビューアー証明書のリージョン要件を満たさない。|S3バケットを公開する|TLS証明書の要件とは無関係。|CloudFrontのキャッシュTTLを短くする|証明書のリージョン要件は変わらない。
Secrets Managerのローテーション|対応するRDS DBの認証情報を定期更新し、アプリが現行の値を取得するようにしたい。|Secrets Managerの対応するローテーション機能を構成し、アプリから必要な権限で現在の値を取得する。|パスワードをAMIへ固定する|更新時にAMIの再作成と配布が必要になる。|Secrets Managerの値を平文ログへ出す|秘密情報の漏洩につながる。|S3のパブリックアクセスを有効化|認証情報の安全な更新とは無関係。
Parameter StoreのSecureString|運用スクリプトが参照する小規模な秘密設定値をKMSで暗号化して管理したい。自動ローテーションは不要。|SecureStringはKMSで値を暗号化し、必要なSSMとKMSの権限で読み出す。|StringListに平文で保存|SecureStringによる暗号化の要件を満たさない。|EC2タグに平文で記録|タグの参照者へ漏洩する可能性がある。|CloudWatchダッシュボードのタイトルに記載|秘密情報の保存先として適切ではない。
# 05 ネットワーク・コンテンツ配信 / VPC
SGで戻り通信が自動許可される|EC2のSGでアウトバウンドTCP443を許可した。EC2自身が開始したHTTPS通信への応答用にインバウンドのエフェメラルポート許可も必要か？|SGはステートフルなので、許可された接続の応答は通常別のSGルールなしで通る。NACLは別途確認する。|必ず全インバウンドポートを公開する|不要なアクセスを許可し危険。|インバウンドTCP443のみを追加する|戻り通信の宛先は通常クライアント側のエフェメラルポート。SGでは応答用ルール自体が不要。|SGを削除する|SGの管理を失う。
NACLで戻り通信のエフェメラルポートを許可|インバウンドTCP443を許可したサブネットのWebサーバーで、NACLのアウトバウンドが443だけのため外部クライアントへの応答が届かない。|NACLはステートレスなのでクライアントのエフェメラルポート範囲へのアウトバウンドも許可する。|SGを変更するだけ|NACLで拒否された通信はSGだけでは許可できない。|アウトバウンドTCP443を重複追加|応答先ポートは通常443ではない。|ルートテーブルのlocal経路を削除|問題の解決にならずVPC内通信にも影響する。
NACLの小さいルール番号を優先|NACLに100番で全TCP許可、200番で特定CIDR拒否を設定したが対象CIDRから接続できる。|NACLは小さい番号から最初に一致したルールを適用する。拒否を許可より前に配置する。|拒否を300番にする|さらに後で評価される。|SGのルール番号を変更|SGには同じ方式の優先順がない。|拒否と許可の番号は無関係|NACLは番号順で評価する。
ルートテーブルの最長プレフィックス一致|0.0.0.0/0をNATへ、10.20.0.0/16をピアリングへ送る経路がある。宛先10.20.1.5の経路は？|より具体的な10.20.0.0/16経路が選択される。|0.0.0.0/0のNAT経路|より具体的な経路が存在する。|すべての経路に同時送信する|通常の経路選択ではない。|送信元IPだけで経路を選ぶ|通常のVPCルート選択は宛先に基づく。
パブリックNAT GatewayとIGWへの経路|プライベートIPv4のEC2がインターネットへ接続できない。標準のゾーン型パブリックNAT Gatewayを使用する構成の必要経路は？|プライベートサブネットのデフォルト経路をNATへ、NATのパブリックサブネットのデフォルト経路をIGWへ設定する。|EC2のデフォルト経路をIGWへ直接向けるだけ|パブリックIPv4がないEC2では通常インターネット通信できない。|NAT GatewayにSGを割り当てるだけ|NAT GatewayにSGを関連付けられない。|VPCのDNS設定を無効にする|インターネット経路を構成しない。
IPv6のegress-only internet gateway|IPv6アドレスを持つEC2からインターネットへ発信できるようにし、外部から新規接続を開始できないようにしたい。|egress-only IGWはIPv6の外向き接続と応答を許可し、外部から開始する接続を防ぐ。|IPv4専用の通常NAT構成だけ|要求はIPv6の外向き通信。|通常IGWへ経路を設定するだけ|IGW自体は新規の外向き限定ゲートウェイではない。|VPCピアリングを作る|インターネットへの出口ではない。
S3 Gateway VPC Endpoint|同一リージョンのS3への大量通信がNAT Gatewayを経由して課金されている。VPC内からNATを使わず接続する標準的な方法は？|S3のゲートウェイエンドポイントをルートテーブルへ関連付ける。通常エンドポイント自体の時間・処理料金はない。|NAT Gatewayを追加する|NAT処理料金を回避する方法ではない。|S3バケットをパブリックにする|NAT経由通信の課金を削減するために公開は不要。|IGWへプライベートIPv4のまま直接接続|通常のインターネット通信要件を満たさない。
インターフェイスエンドポイントのSGにTCP443を許可|Secrets ManagerのインターフェイスエンドポイントでプライベートDNS解決は成功するが、エンドポイントENIへのTCP443接続がSGで拒否される。|エンドポイント側のSGで呼び出し元からのTCP443を許可する。IAM権限は別途必要。|S3 Gateway Endpointを追加する|Secrets Managerのインターフェイス接続に対するSGを修正しない。|EC2に管理者IAM権限を付与するだけ|TCP接続を許可するSGとは別。|エンドポイントのDNSを無効化する|名前解決が成功している状況のTCP拒否を解消しない。
インターフェイスエンドポイントのプライベートDNS|AWSサービスの通常のリージョンDNS名を使ったSDK通信をVPCエンドポイントのプライベートIPへ向けたい。VPCのDNS機能は有効。|対応するインターフェイスエンドポイントでプライベートDNSを有効にする。|VPCのDNS解決を無効化|通常の名前解決ができなくなる。|S3バケットポリシーだけ変更|対象サービスのDNS解決を変更しない。|インターネットからの受信をSGで許可|プライベートDNSの設定ではない。
VPC Peeringは推移的でない|VPC AとB、BとCがピアリング済み。AとCは直接接続されていない。AからBのピアリングを経由してCへ通常ルーティングできるか？|VPCピアリングは推移的ではない。AとCの直接ピアリングやTransit Gateway等を設計する。|Bのルート追加だけで推移的に転送できる|通常のピアリングでは推移的ルーティングをサポートしない。|AのSGを全許可すれば通る|ネットワーク経路の制約はSGでは解消しない。|CloudFrontを作成すればVPC全体が接続される|CDNでありVPC間ルーターではない。
# 05 ネットワーク・コンテンツ配信 / DNSと配信
Route 53 Resolver inbound endpoint|オンプレミスのDNSサーバーからVPCに関連付けたプライベートホストゾーンの名前を解決したい。VPN等の経路は確立済み。|オンプレミスからVPCへDNS問い合わせを転送するためのinbound endpointを構成する。|outbound endpointのみ|VPC側から外部DNSへ問い合わせを転送する方向。|パブリックホストゾーンに全内部レコードを登録|内部の名前を公開する必要はない。|VPC Flow Logsを有効化|通信の記録でDNSの転送機能ではない。
Route 53 Resolver outbound endpointと転送ルール|VPC内のEC2からcorp.example.internalをオンプレミスDNSへ問い合わせたい。ハイブリッド接続は確立済み。|outbound endpointと対象ドメインの転送ルールを設定しVPCへ関連付ける。|inbound endpointだけ|オンプレミスからVPC方向のDNS問い合わせ用。|CloudFrontのオリジンをオンプレDNSにする|DNSフォワーディングとは異なる。|S3 Gateway Endpointを作成|S3向けの通信経路。
Route 53のエイリアスレコード|example.comというゾーン頂点をALBへ向けたい。通常のCNAMEはゾーン頂点に設定できない。|対応するAWSリソースを指定するRoute 53のAliasレコードを使用する。|ゾーン頂点に通常CNAMEを設定|ゾーン頂点のSOA・NSとの共存制約に反する。|ALBのIPを取得し固定Aレコードを作る|ALBのIPは変更されうる。|MXレコードでALBへ向ける|メール配送先の指定。
Route 53 weighted routing|旧環境と新環境のDNSレコードに対し、概ね9対1の割合でDNS応答を分けたい。|重み90と10のレコードを設定する。DNSキャッシュがあるためHTTP要求の厳密な割合ではない。|Failover routing|主系と待機系の切り替えが主目的。|Geolocation routing|利用者の地理的位置で応答を選択する。|Simple routingのみ|指定重みによる配分を設定しない。
Route 53 latency routing|同じアプリを東京と米国に配置した。利用者にAWSのレイテンシ情報に基づいて低遅延なリージョンの応答を返したい。|Latency routingは利用者からAWSリージョンへのレイテンシに基づいてレコードを選択する。|Multivalue answer routing|複数の正常な値を返す方式で低遅延リージョンの選択ではない。|Failover routing|主系と待機系を切り替える。|固定の単一Aレコード|利用者の位置に応じたレイテンシ選択をしない。
CloudFrontのキャッシュポリシーで必要なクエリ文字列のみ含める|商品詳細APIはproductIdで応答が変化するが、utm_sourceは応答に影響しない。キャッシュヒット率を高めつつ内容の混同を防ぎたい。|キャッシュキーにproductIdを含め、応答に影響しない追跡パラメータは除外する。|すべてのクエリ文字列を除外|異なる商品が同じキャッシュキーになりうる。|すべてのクエリ文字列を含める|不要なパラメータの違いでキャッシュが分散する。|オリジンのIPを固定する|キャッシュキーの問題を解決しない。
