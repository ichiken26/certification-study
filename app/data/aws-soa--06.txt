# 04 セキュリティ・コンプライアンス / 複数選択実践
@multi|公開S3バケットへのデータ流出が発生した。組織全体で意図しない公開を抑止し、構成違反を監視し、過去の操作を監査したい。対応を3つ選べ。|予防、継続検知、操作監査を組み合わせる。|1,3,5|S3 Block Public Accessを対応する管理範囲で有効にする|意図しない公開アクセスを制限する。|全バケットの暗号化を解除する|公開認可を解決せず機密性を悪化させる。|AWS Configの関連ルールで公開状態を評価する|非準拠の構成を検知する。|CloudWatchの全ログを削除する|監査証跡を損なう。|CloudTrailの管理イベントと必要なデータイベントを収集する|構成変更や対象オブジェクトの操作履歴を確認する。
# 05 ネットワーク・コンテンツ配信 / 複数選択実践
@multi|プライベートサブネットのEC2から同一リージョンのS3へのアクセスだけを許可する。インターネット経由のNAT処理費用も避けたい。対策を2つ選べ。|S3ゲートウェイエンドポイントを利用し、アクセスを許可対象へ制限する。|1,3|S3 Gateway Endpointを対象ルートテーブルへ関連付ける|対象のS3通信をゲートウェイエンドポイントへ送る。|EC2へElastic IPを必ず付ける|この設計では不要である。|エンドポイントポリシーで必要なS3操作と対象バケットを限定する|エンドポイントを介するアクセス範囲を制限する。|VPCのすべてのSGを無条件許可する|最小権限に反する。|S3バケットを公開する|IAM等の非公開認可でアクセスできる。
# 01 モニタリング・ロギング・修復 / 複数選択実践
@multi|EC2上のアプリが遅い。標準EC2 CPU指標は低いがOSのメモリやディスクI/O待ちは未収集である。診断に必要な対策を2つ選べ。|OSレベルのメトリクスを収集し、EBSおよびOSのI/O情報を照合する。|2,5|CPUが低いため性能問題はないと判断する|CPU以外の資源や待ちが原因になり得る。|CloudWatch Agent等でOSメモリ指標を収集する|標準EC2指標だけではゲストメモリを把握できない。|すべてのEBSを直ちに削除する|データ損失を招き診断にならない。|ログ保持期間をゼロにする|性能問題の原因を解決しない。|EBSのキュー長やI/O指標とOSのiostat等を確認する|ストレージの待機と実際の負荷を切り分ける。
