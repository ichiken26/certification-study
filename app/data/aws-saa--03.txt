# 01 IAM・基礎 / 設計演習
ロールの信頼ポリシーと呼び出し元のsts:AssumeRole許可を設定する|アカウントAのIAMロールからBのロールを引き受けてBのS3を読む。BのロールにはS3読み取り権限がある。追加する設定は？|クロスアカウントのAssumeRoleでは引き受け先が呼び出し元を信頼し、呼び出し側にもsts:AssumeRoleの許可が必要。|AのロールだけにS3のGetObject許可を追加|Bのロールの信頼関係が設定されない。|Bのロールにsts:AssumeRoleを許可するだけ|B側のアクセス許可ポリシーは信頼ポリシーの代わりにならない。|S3バケットをパブリック公開する|要求するロールによる認証を満たさず、不必要にアクセス範囲を広げる。
EC2のインスタンスプロファイルにIAMロールを付け、S3とKMSへの最小権限を付与|EC2アプリがカスタマーマネージドKMSキーによるSSE-KMSのS3データを読みたい。長期キーは不可。キーへのアクセスも許可できる。|EC2のロールにGetObjectとkms:Decryptを許可し、KMSキーポリシーも対応させる。|EC2のSGにS3のバケット名を設定|SGはネットワーク通信の制御でAWS API認可を行わない。|S3のGetObject許可のみ|SSE-KMSでの復号にはKMSの権限も必要。|IAMユーザーのアクセスキーをAMIに保存|長期キーをイメージに置く要件違反。
# 02 ネットワーク / 設計演習
ALBを公開しEC2とDBはプライベートサブネットへ配置|インターネットからHTTPSでWebアプリにアクセスし、EC2とRDSは直接公開しない。最小の入口を作りたい。|公開ALBだけが外部接続を受け付け、EC2はALBのSGからの通信、DBはアプリSGからの通信に限定する。|すべてのEC2とRDSにパブリックIPを割り当てる|直接公開を避ける要件に反する。|ALBを内部向けにしてIGWを削除|インターネットからの公開入口にならない。|NAT GatewayにインバウンドHTTPSを受信させる|NAT Gatewayは外部から開始するWeb接続の受付に使えない。
プライベートサブネットにInterface Endpointを設置しPrivate DNSを有効化|インターネット接続のないVPCでSecrets Manager SDKの標準サービス名をそのまま使いたい。|Private DNSによって標準のサービスDNS名がエンドポイントのプライベートIPへ解決される。|Gateway EndpointをSecrets Manager用に設定|Secrets ManagerはInterface型を利用する。|Private Hosted Zoneに公開IPだけを登録|インターネットへの経路なしでは公開IPへ接続できない。|NAT Gatewayを追加してIGWを削除|パブリックNATのインターネット経路にはIGWが必要。
# 03 コンピューティング / 設計演習
ALBと複数AZのASG、セッションはElastiCacheへ保存|EC2のWebアプリが各インスタンスのメモリにログインセッションを持つため、増減や障害でログアウトする。どの設計が適切？|セッションを共有外部ストアに置くとEC2をステートレスにでき、別インスタンスでリクエストを処理できる。|ASGを単一AZに制限しALBのスティッキーセッションを使う|障害で対象インスタンスが失われるとメモリ上のセッションも失われる。|EC2のインスタンスタイプだけを大型化|セッション消失問題と単一障害点を解消しない。|NLBの固定IPを利用|固定IPはセッションの永続化を実現しない。
SQSのキュー長を基準にFargateワーカーのタスク数を調整|動画処理が30分以上かかる。需要に応じて増減し、OS管理を避けてジョブ消失にも備えたい。|SQSで受付を分離し、Fargateで長時間コンテナ処理。Visibility Timeoutの延長と冪等性も設計する。|Lambdaで1回の実行に全30分の処理を行う|Lambdaの1回の実行上限は15分。|単一EC2上で同期的にすべて処理する|OS管理が必要で受付時の負荷集中や単一障害点に弱い。|ALBで長時間ジョブをキューに永続化する|ALBはリクエストを配送するが永続ジョブキューではない。
# 04 ストレージ / 設計演習
S3へ署名付きPUT URLを発行しブラウザから直接アップロード|画像投稿APIのEC2が大容量ファイルの転送で逼迫する。S3バケットは非公開のまま維持したい。|APIは短期の署名付きURLを発行し、ブラウザが直接S3に送る。CORSやアップロード制限は別途設定する。|EC2のEBSを大型化|EC2経由の転送負荷自体は減らない。|S3バケットのPutObjectを匿名全員に許可|不必要な公開書き込みと悪用リスクがある。|CloudFrontキャッシュだけを延長|アップロード経路を分離しない。
S3 Object Lockとバージョニングを用いた保持|法的監査の原本を7年間、管理者の誤操作でも削除できないようにしたい。|Complianceモードの保持を対象バージョンへ適用することで保持期間中の削除を制限できる。|S3 StandardからStandard-IAに移行|アクセス頻度に応じた料金変更であり削除防止ではない。|S3バージョニングのみ|権限のある管理者は個別バージョンを削除できる。|S3のCRRだけ|複製は改ざん防止の保持機構ではない。
# 05 データベース / 設計演習
RDS Multi-AZとRead Replicaを組み合わせる|RDS for PostgreSQLでAZ障害への自動切替と、重いSELECTの読み取り分散を両方実現したい。|従来型Multi-AZは同期待機系、Read Replicaは読み取り分散を担当する。|Single-AZにRead Replicaだけ追加|通常のRead Replicaだけではプライマリの自動フェイルオーバー要件を満たさない。|従来型Multi-AZ DBインスタンス配置のみ|待機系は通常の読み取り処理に使えない。|RDS Proxyのみ|接続管理でありDBの読み取りレプリカや待機系を作らない。
RDS ProxyとLambdaの同時実行数制御|Lambdaの急増でPostgreSQLへの接続上限を超える。DBスキーマ変更は避けたい。|プロキシで接続をプールし、必要に応じ同時実行数を制御することで接続集中を抑える。|DynamoDB DAXを追加|DAXはDynamoDB用でPostgreSQLの接続管理をしない。|S3 Transfer Accelerationを有効化|S3転送高速化でありDB接続数に関係しない。|RDSのバックアップ保持期間を延ばす|接続枯渇の対策にならない。
# 06 非同期・サーバーレス / 設計演習
S3イベントをSQSへ送りLambdaで冪等に処理|画像をアップロードするとサムネイルを作る。大量投稿と一時的な処理失敗に対応し、イベントの重複も許容したい。|SQSで処理をバッファし、Lambdaが非同期処理する。重複に備えて同じ画像IDを安全に処理する。|同期APIがすべての画像処理完了を待つ|受付と処理を分離できず負荷集中に弱い。|SNSのメール通知を使って手作業で変換|自動処理要件を満たさない。|S3のライフサイクルでサムネイルを生成|ライフサイクルはストレージクラス移行・削除などを管理する機能。
SQS FIFOとメッセージグループID、DBの条件付き更新|同じ注文内の処理順序を保ちつつ、他の注文は並列化し、重複した処理で二重引き落としをしないようにしたい。|注文IDをグループIDにして順序を保ち、DBで冪等性を確保する。FIFOだけで副作用の厳密な一度実行は保証できない。|SQS Standardのみ|順序はベストエフォートで、重複も起こりうる。|SNS Standardのみ|注文単位の厳密な順序・永続的な重複制御の要件を満たさない。|Lambdaのメモリに処理済みIDを保存|実行環境の再生成や並列実行で共有できない。
# 07 セキュリティ・運用 / 設計演習
CloudTrailの組織証跡を中央ログアカウントのS3へ保存|複数アカウントの管理API操作を監査し、各アカウントの管理者に監査ログを消されにくくしたい。|組織証跡で記録を統合し、別アカウントにログを集中して書き込み・削除権限を分離する。|EC2のCloudWatch CPUメトリクスを保存|CPUメトリクスにはAWS管理APIの呼び出し主体は記録されない。|各アカウントのローカルEC2ディスクにのみ保存|一元監査できず削除や障害の影響を受ける。|VPC Flow Logsのみを保存|ネットワークフローは管理APIの操作履歴とは異なる。
WAFをALBに関連付けマネージドルールでHTTPを検査|公開APIがSQLインジェクションを含むHTTPリクエストを受けている。アプリの前段で検査・拒否したい。|WAFのルールでHTTPのヘッダー、URI、本文等を検査する。アプリ自身のパラメータ化クエリも重要。|NACLでTCP 443を全面拒否|正規のHTTPSリクエストも遮断される。|Shield Standardだけを利用|DDoS保護はSQLインジェクションのルール検査とは異なる。|KMSキーをローテーション|暗号鍵管理でありHTTPリクエストを検査しない。
# 08 DR・コスト / 設計演習
別リージョンにAurora Global Databaseと縮小したアプリ環境を用意|リージョン災害対策としてデータの損失を小さくし、復旧時にアプリ基盤をゼロから作りたくない。平時のDR費用は抑えたい。|データのクロスリージョン複製とWarm Standbyを組み合わせ、復旧時に昇格・増強する。具体的なRPO/RTOは検証する。|同一AZのEBSだけにバックアップ|リージョン障害で同時に利用できなくなる可能性がある。|年1回の手動バックアップのみ|データ損失を小さくする要件を満たしにくい。|DR側で全本番容量を常時稼働し全トラフィックを処理|高い可用性を狙えるが、平時費用を抑える条件に対して過剰。
CloudFrontでキャッシュしS3のオリジンアクセスを減らす|世界中の利用者が同じ大きな静的ファイルを繰り返し取得する。オリジン負荷と利用者の遅延を抑えたい。|CDNのエッジキャッシュから配信する。キャッシュヒット率を高めることでオリジンへのリクエストを削減する。|NAT Gatewayを追加|外部通信経路でありCDNキャッシュを提供しない。|S3をEBSに移して単一EC2から配信|オリジン側の管理負荷や可用性の問題が増える。|毎回異なるランダムクエリをキャッシュキーに加える|同一コンテンツでもキャッシュが分散しヒット率が低下する。
# 09 周辺サービス / 設計演習
S3にParquetで保存し日付でパーティション分割、Athenaで集計|月に数回だけ数TBのアクセスログをSQL分析する。常時稼働する分析基盤を持たずスキャン量も減らしたい。|Athenaで必要な日付・列だけをスキャンする。列指向圧縮とパーティションで読み取り量を削減できる。|すべてのCSVを毎回全件Scanする|不要データまで読み取り課金と時間が増える。|ログを単一EC2のメモリへすべてロードする|数TBのデータに対して大規模メモリや運用が必要。|DynamoDBへ入れて毎回テーブル全件をScanする|大量の分析集計用途では非効率な読み取りになる。
DMSのフルロードとCDCで移行し、切替前に差分同期を確認|オンプレミスPostgreSQLをRDSへ移す。現行DBの停止時間をできるだけ短くしたい。|フルロード後も変更を継続複製し、切替時の差分を小さくする。必要なスキーマ・機能の移行も検証する。|アプリ停止後に初めて全DBをダンプする|データ量が大きいと停止時間が長くなる。|DataSyncで稼働中DBのファイルだけをコピーする|DBの整合性と継続的な変更複製は保証されない。|S3 Transfer Accelerationを有効化するだけ|DB移行と変更データの同期を実施しない。
